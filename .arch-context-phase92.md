## 2. Conventions the architect must follow

Sources: `backend/CLAUDE.md`, `frontend/CLAUDE.md`, root `CLAUDE.md`, and the trust code as it stands.

### 2.1 Tenancy — schema-per-tenant only

Quoted, `backend/CLAUDE.md` › Multitenancy: "Schema-per-tenant isolation within a single Postgres database. Every tenant — regardless of billing tier — gets a dedicated `tenant_<hash>` schema. **There is no shared schema.**" and "**Isolation model**: Pure schema boundary — no `@Filter`, no RLS policies, no `tenant_id` columns. Standard `JpaRepository.findById()` works correctly."

Plainly: **shared-schema, RLS, Hibernate `@Filter`/`@FilterDef`, `TenantAware` and `tenant_id` columns do not exist.** An older architecture template mentions them; ignore it. New tenant tables carry no tenant column and no policy. Tenant resolution: JWT org claim → `org_schema_mapping` → `RequestScopes.TENANT_ID` (ScopedValue) → connection `search_path`. Portal read-model tables are the exception: they live in the global `portal` schema and are keyed by `customer_id` (+ `matter_id`); `architecture/PortalReadModelOrgScopingGuardTest` guards their scoping.

### 2.2 Entity pattern (as in `TrustTransaction`, full source §3.2)

- Plain `@Entity @Table(name = "snake_case")`, **no Lombok**, no base class, no tenant column.
- `@Id @GeneratedValue(strategy = GenerationType.UUID) private UUID id;`
- Foreign keys are **bare `UUID` columns** (`trustAccountId`, `customerId`, `projectId`) — no `@ManyToOne` associations.
- Money: `BigDecimal`, `@Column(precision = 15, scale = 2)`; rates `numeric(5,4)`.
- Dates: business dates are `LocalDate` (`transaction_date` is an SA business date); timestamps `Instant` (`timestamptz`), set in `@PrePersist`/`@PreUpdate`.
- `protected` no-arg constructor for JPA + one public constructor with required fields; mutation through intention methods (`addDeposit`, `setStatus`), getters only otherwise.
- Status/type columns: `String` + DDL CHECK (trust transactions, lines, investments, runs) **or** `@Enumerated(EnumType.STRING)` Java enum + DDL CHECK (`TrustAccountType`, `ReconciliationStatus`, `InvestmentBasis`). Both exist; new code should say which and why (ADR-238 "entity type varchar vs enum").
- Naming: "Entities: domain name … no `Entity` suffix"; "Use Java records for DTOs"; DTO records are **nested in the service** in this module (`TrustTransactionService.RecordDepositRequest`, `…Response`), wire names use `clientId` / `matterId` while columns stay `customer_id` / `project_id`.

### 2.3 Repository pattern

- `interface XRepository extends JpaRepository<X, UUID>`; derived finders + `@Query` JPQL text blocks; native SQL only where needed (window functions, `date_trunc`) with `nativeQuery = true` and interface projections (`ClientHistoryRow`, `TrustMonthlyMovementProjection`, `MatterBalanceRow`, `CustomerTypeTotalRow`).
- Row locks: `@Lock(LockModeType.PESSIMISTIC_WRITE)` finder named `…ForUpdate` (`findByIdForUpdate`, `findByAccountAndCustomerForUpdate`, `findByPlacementTransactionIdForUpdate`). The client card lock serialises every posting for a client; lock order for investments is placement PAYMENT row → investment row (`TrustInvestmentService.java:234-246`).
- Nullable binds in native SQL are `CAST(:x AS type)` on both occurrences.

### 2.4 Request context, services, controllers

- "Never use `ThreadLocal` for request-scoped context — use `ScopedValue` via `RequestScopes`". Used here: `RequestScopes.requireMemberId()`, `hasCapability("…")`, `getTenantIdOrNull()`, `getOrgIdOrNull()`; background work uses `RequestScopes.runForTenant(...)` / `TenantTransactionHelper.executeInTenantTransaction`.
- Time: inject `Clock`; `LocalDate.now(clock)` (SA clock, ArchUnit bans zone-less `now()` since #1716). Note `Instant.now()` still appears for `approvedAt`.
- "Controllers are **HTTP adapters only**. Every controller method must be a one-liner that delegates to a single service method and wraps the result in `ResponseEntity`." No repositories, no branching, no private helpers in controllers; enforced by ArchUnit (`LayerDependencyRulesTest`).
- Constructor injection only; `@Transactional` on service methods (`readOnly = true` for reads).
- "Avoid premature abstractions — do not create provider/adapter patterns until there are two concrete implementations (YAGNI)."

### 2.5 Exceptions

"Services throw semantic exceptions from the `exception/` package — Spring auto-renders them as RFC 9457 ProblemDetail responses." Never build `ProblemDetail` in a controller or service.

| Exception | HTTP | Use |
|---|---|---|
| `ResourceNotFoundException(entityNameOrEntityNoun, id)` | 404 | not found or hidden |
| `ResourceConflictException` | 409 | duplicate / state conflict |
| `ForbiddenException(title, detail)` | 403 | missing capability |
| `InvalidStateException(title, detail)` | 400 | bad transition / business refusal (every trust refusal uses this) |
| `ModuleNotEnabledException` | (module gate) | thrown by `VerticalModuleGuard.requireModule` |
| `BankStatementParseException` (in `T/reconciliation/parser/`) | 422 | `GlobalExceptionHandler.java:150` |

### 2.9 Frontend conventions

- "Prefer React Server Components (RSC) by default — only add `"use client"` when needed"; "Never access `params` without `await`"; never pass functions or component references Server → Client.
- **Server actions** live beside the route in `actions.ts` with `"use server"`; they call the backend only through `api` from `@/lib/api` ("Centralized fetch wrapper that attaches Bearer JWT from auth context"; Keycloak mode routes via the gateway). Pattern (`FE/transactions/actions.ts:87-108`): `try { await api.post(...); revalidatePath("/", "layout"); return { success: true }; } catch (error) { return { success: false, error: error instanceof Error ? error.message : "Failed to …" }; }` returning `ActionResult`. Multipart upload is the one raw `fetch` (`FE/reconciliation/actions.ts:63-117`).
- Wire mapping happens in the action: form `customerId`/`projectId` → body `clientId`/`matterId`.
- Lists return bare JSON arrays for reconciliations and bank statements (G89-F17; pinned by `frontend/__tests__/trust-reconciliation-wire-shapes.test.ts`); paginated endpoints use the VIA_DTO shape `{ content, page: { totalElements, totalPages, size, number } }`.
- Client fetching in dialogs: SWR wrapping server actions, never direct fetch.
- Forms: Zod + React Hook Form + Shadcn `Form`; "Keep schemas in `lib/schemas/` — never inline Zod schemas in components" (`frontend/lib/schemas/trust.ts`). Types in `frontend/lib/types/trust.ts`.
- Vocabulary: "Write the legal word in the source — Matter, Client, Fee note…"; no terminology layer (ADR-338). Colours: slate + teal; base primitives from `@b2mash/ui`; `radix-ui` unified package; never two adjacent `DialogTrigger asChild` siblings.
- Phase 90 primitives to use as they stand: `PageHeader`, `StatCard`, `EmptyState`, `DataTable`, chart kit (`components/trust/trust-balance-trend-chart.tsx`). Do not pre-empt Phase 91.
- Known stack issue: next@16.2.6 lost the React ping — `revalidatePath` updates can stall on cold servers; never mask with timeouts/reload.
- Gate: `pnpm lint && pnpm build && pnpm test` **plus** `format:check` (prettier is a separate CI step); full vitest, not narrowed. UI slices re-run the legal Playwright suites.

### 2.10 Test conventions

- Integration test header: `@SpringBootTest @AutoConfigureMockMvc @Import(TestcontainersConfiguration.class) @ActiveProfiles("test") @TestInstance(PER_CLASS)`; there is **no shared base class** — each class provisions its own tenant in `@BeforeAll` (`provisioningService.provisionTenant(ORG_ID, "…", null)`), unique `ORG_ID` per class (e.g. `"org_trust_txn_svc_test"`). `TrustTransactionServiceTest` also uses `@RecordApplicationEvents`.
- "**Do NOT use Testcontainers**" — embedded Postgres (zonky) + `InMemoryStorageService`, both from `TestcontainersConfiguration` (the class name is historical). ArchUnit `TestConventionsTest` fails on any Testcontainers import.
- Email: `GreenMailTestSupport.getInstance()` singleton, dynamic port published as `greenmail.smtp.port` ("never start your own instance, never hardcode the port").
- Helpers in `backend/src/test/java/.../testutil/`: `TestMemberHelper.syncMember`, `TestJwtFactory.ownerJwt/adminJwt/memberJwt`, `TestEntityHelper`, `TestCustomerFactory.createActiveCustomer` (customers default to PROSPECT), `TestIds`, and trust-specific:

  - `TestTrustBalanceFactory.seedTrustBalance(...)` — creates an INVESTMENT account + a card + one deposit for collections tests (writes the card directly).
- Service-level calls run inside `ScopedValue.where(RequestScopes.TENANT_ID, …).where(MEMBER_ID, …).where(CAPABILITIES, …).run(...)` or via MockMvc with a JWT.
- "Never assert an exact global count over accumulating shared-tenant state" — id-scope or baseline+delta. An invariant harness that sums a whole trust account in a PER_CLASS tenant must use **its own trust account per test** (the equation is per account) or it will count siblings' rows.
- Error-path tests assert ProblemDetail fields, not only status. Names: `*IntegrationTest`, `*ServiceTest`, `*Test`; never `Tests`.
- Fixtures: bank CSV samples in `backend/src/test/resources/fixtures/trust/{absa,fnb,nedbank,standard-bank,generic}-sample.csv`.
- Merge bar: full `./mvnw verify` via `backend/scripts/verify.sh` (preflight + caffeinate); never overlap a Maven verify with an E2E run; reproduce-before-fix with a red test first (root CLAUDE.md §4).

```java
  public void addDeposit(BigDecimal amount, LocalDate transactionDate) {
    Objects.requireNonNull(amount, "amount must not be null");
    if (amount.compareTo(BigDecimal.ZERO) <= 0) {
      throw new IllegalArgumentException("amount must be positive");
    }
    this.balance = this.balance.add(amount);
    this.totalDeposits = this.totalDeposits.add(amount);
    updateLastTransactionDate(transactionDate);
  }

  /**
   * Subtracts the given amount from the balance. Used for inter-client transfers. Running totals
   * (totalPayments, totalFeeTransfers) are NOT updated here — those are updated by type-specific
   * methods added in future slices (PAYMENT, FEE_TRANSFER transaction types).
   */
  public void debitBalance(BigDecimal amount, LocalDate transactionDate) {
    Objects.requireNonNull(amount, "amount must not be null");
    if (amount.compareTo(BigDecimal.ZERO) <= 0) {
      throw new IllegalArgumentException("amount must be positive");
    }
    this.balance = this.balance.subtract(amount);
    updateLastTransactionDate(transactionDate);
  }

  public void addPayment(BigDecimal amount, LocalDate transactionDate) {
    Objects.requireNonNull(amount, "amount must not be null");
    if (amount.compareTo(BigDecimal.ZERO) <= 0) {
      throw new IllegalArgumentException("amount must be positive");
    }
    this.balance = this.balance.subtract(amount);
    this.totalPayments = this.totalPayments.add(amount);
    updateLastTransactionDate(transactionDate);
  }

  public void addFeeTransfer(BigDecimal amount, LocalDate transactionDate) {
```

```java
package io.b2mash.b2b.b2bstrawman.verticals.legal.trustaccounting.transaction;

/**
 * Client-facing labels for a trust transaction type (tenant {@code chk_trust_txn_type}). Same copy
 * as the portal trust page ({@code portal/lib/labels.ts} TRUST_TRANSACTION_TYPE_LABELS), so the
 * client reads one vocabulary in the portal, the trust-activity email (633C D6) and the Statement
 * of Account's trust Payments table (G89 W2-c3).
 */
public final class TrustTransactionTypeLabels {

  private static final Map<String, String> LABELS =
      Map.of(
          "DEPOSIT", "Deposit",
          "PAYMENT", "Payment",
          "REFUND", "Refund",
          "FEE_TRANSFER", "Fee transfer",
          "INTEREST_CREDIT", "Interest credited",
          "INTEREST_LPFF", "Interest to LPFF",
          "TRANSFER_IN", "Transfer in",
          "TRANSFER_OUT", "Transfer out",
          "REVERSAL", "Reversal");

  private TrustTransactionTypeLabels() {}

  /**
   * The label for {@code transactionType}; an unmapped value falls back to sentence case ({@code
   * "SOME_TYPE"} → {@code "Some type"}), never the raw enum. Null/blank stays null so a template
   * can print its own placeholder.
   */
  public static String label(String transactionType) {
    if (transactionType == null || transactionType.isBlank()) {
      return null;
    }
    String label = LABELS.get(transactionType);
    if (label != null) {
      return label;
    }
    String text = transactionType.trim().replace('_', ' ').toLowerCase(Locale.ROOT);
    return Character.toUpperCase(text.charAt(0)) + text.substring(1);
  }
}
```

**`tenant/V15__g89_trust_investment_cancelled.sql`** (full file — the constraint-swap pattern to copy)
```sql
-- G89-F87 (D41): a trust investment whose placement PAYMENT is rejected is CANCELLED (terminal).
-- The investment is created ACTIVE while its placement still awaits approval; rejecting the
-- placement used to leave it ACTIVE on the s86 register, in getMaturing and in the Section 35 data
-- pack with no money behind it. chk_trust_invest_status is a baseline CHECK over three values; swap
-- it for four. Idempotent, and every catalog guard is scoped to current_schema() (BASELINE.md §5).
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM pg_constraint c JOIN pg_namespace n ON n.oid = c.connamespace
             WHERE c.conname = 'chk_trust_invest_status' AND n.nspname = current_schema()
               AND pg_get_constraintdef(c.oid) NOT LIKE '%CANCELLED%') THEN
    ALTER TABLE trust_investments DROP CONSTRAINT chk_trust_invest_status;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_constraint c JOIN pg_namespace n ON n.oid = c.connamespace
                 WHERE c.conname = 'chk_trust_invest_status' AND n.nspname = current_schema()) THEN
    ALTER TABLE trust_investments ADD CONSTRAINT chk_trust_invest_status
      CHECK (status IN ('ACTIVE', 'MATURED', 'WITHDRAWN', 'CANCELLED'));
  END IF;
END $$;
```

### 3.7 Reversal flow (for the reproduction tests)

Entry: `POST /api/trust-transactions/{id}/reverse` (`MANAGE_TRUST`) → `TrustTransactionService.reverseTransaction(UUID transactionId, String reason)` `:1224-1434`.

1. Guards: blank reason `:1228`; original locked `findByIdForUpdate` `:1233-1236`; `TRANSFER_IN` refused ("reverse the paired TRANSFER_OUT") `:1240-1244`; account CLOSED refused `:1253`; original must be `APPROVED` `:1258-1261` — **so a `RECORDED` DEPOSIT, INTEREST_CREDIT, INTEREST_LPFF or seeded row can never be reversed** (deposits are saved RECORDED at `:361` and never become APPROVED; test `reverseCreditTransaction_requiresApproval` at `TrustTransactionServiceTest.java:860` shows how existing tests obtain an APPROVED credit — read it before designing the repro); already reversed (`reversedById != null || existsByReversalOf`) `:1266-1270`; a PAYMENT that placed an investment is never reversible `:1280-1290`.
2. `TRANSFER_OUT` → `reverseTransferOut` `:1441-1601`: two `REVERSAL` rows `RECORDED` (`:1534`, `:1551`), both originals set `REVERSED` `:1556-1562`, source card credited `:1568`, target card debited `:1574` (target must still hold the money — `TrustMatterDebitGuardIntegrationTest.java:315`). Cashbook-neutral before and after.
3. Type split `:1299-1313`: debit types (`PAYMENT`, `TRANSFER_OUT`, `FEE_TRANSFER`, `REFUND`) → reversal status `RECORDED`; credit types (`DEPOSIT`, `TRANSFER_IN`, `INTEREST_CREDIT`) → `AWAITING_APPROVAL`; anything else (**`INTEREST_LPFF`**, `REVERSAL`) throws `InvalidStateException("Cannot reverse transaction", "Transaction type … cannot be reversed")` `:1309-1312`.
4. A new `TrustTransaction` of type `"REVERSAL"`, same amount/client/matter/counterparty, reference `REV-<orig>`, description = reason, dated `LocalDate.now(clock)` (not the original's date), `reversalOf = original.id` `:1318-1335`.
5. **Debit reversal (immediate)** `:1340-1411`: original gets `reversedById` and status `REVERSED` `:1341-1343` → it drops out of every `status IN ('RECORDED','APPROVED')` sum, so the **cashbook rises by the amount** (the REVERSAL row itself counts 0). FEE_TRANSFER also cascades to the fee note: finds the `payment_events` row (provider `trust_fee_transfer`, reference, amount) and calls `invoiceService.reversePayment` `:1363-1410`. Because the reversal is dated today and the original simply vanishes from the sums, **a back-dated as-at balance changes retroactively** (relevant to month locking, E6).
6. **Credit reversal (awaiting approval)** `:1412-1414`: original stays `APPROVED`; nothing else is written.
7. **How a pack version bump is done** (ADR-356; `backend/CLAUDE.md` › Pack reconcile contract; worked v2/v3 at `:64-90`):
1. Change the Java factory (`…Definition()`), add/remove slugs in `SLUGS` (`:54-62`).
2. `PACK_VERSION++`.
3. Add `entry(slug, field, fromHash, toHash)` rows to `RECONCILE` — `field` ∈ `name` / `description` (strings) or `parameterSchema` / `columnDefinitions` / `templateBody` (whole-value `sha256:` + `ContentHashUtil.hashOf`). Chain is **cumulative**: re-point every older entry's `to` for that (slug, field) to the new head and add one entry from the previous head. Update the head-hash constant.
4. Existing tenants: `doSeed` → `reconcileAppliedPack` → `packVersionGate.backfillAndTryOpen(PackType.REPORT, PACK_ID, appliedVersion, …)` (`:142`) → `reconcileExistingPack` (`:154`) applies each entry under the one rule (write only where current == `from`). Fresh tenants: `upsertReport(shipped(slug))` for every slug, then `recordReportPackApplication(PACK_ID, PACK_VERSION)` + `packVersionGate.recordIfAbsent`.
5. **Adding a new report slug or deleting one for existing tenants is not covered by field-level entries** — the current reconcile only edits fields of existing rows. A new slug (Rule 54.28 schedule, unidentified-deposit age analysis) and the removal of `interest-allocation` need an explicit step in `reconcileExistingPack` (precedent for an additive override: `FieldPackSeeder.applyReconcileEntry` "membership" upsert) — an architect ruling. With no production tenants the cost is low, but the contract says "Fresh tenants only is a review reject".
6. Ship the seeder reconcile test: `TrustReportPackSeederIntegrationTest` (installed at n−1 → reconcile to n; a firm-edited row survives; equal version is a no-op). Frozen prior bodies live in `backend/src/test/java/.../trustaccounting/report/TrustReportsV1.java` and `TrustReportsV2.java`; a v4 bump adds `TrustReportsV3`.
Wiring: `seedForTenant` is called from `TenantProvisioningService` and `PackReconciliationRunner` right after the standard report pack (Phase 89 §14.3.1).

````markdown
# ADR-374: First paint of the stored theme comes from a blocking `<head>` script; `next-themes` stays the runtime owner

**Status**: Accepted (refines [ADR-371](ADR-371-dark-mode-light-default.md) Rationale point 1; ADR-371's decision is unchanged)

**Context**:

ADR-371 puts the `next-themes` `ThemeProvider` inside `<body>` in `frontend/app/layout.tsx`, because `<AuthProvider>` wraps `<html>`. It relies on next-themes' own inline script to set the `dark`/`light` class on `<html>` before the first paint. Slice 637B's real-browser observation (PR #1760, head `1b78ae412`) showed that assumption does not hold under a slow, cold load:

- **Setup.** `kazi-theme=dark` stored, browser cache disabled, CPU throttled 4×, network Slow 4G, then a reload of `/org/e2e-test-org/dashboard`.
- **Result.** In **3 of 10** runs a whole-viewport light frame was presented before the dark frames (mean luminance 246 against about 20 for dark). Every such frame came after the new document's first script ran.
- **Cause.** The streamed HTML chunk ended before next-themes' script inside `<body>`. The browser painted `<body>` with no theme class, so it showed the light `--background`, until that script arrived and ran.
- Evidence: `qa_cycle/evidence/phase90-ui/637B/run1-1b78ae412/` (`README.md`, `fouc-diag-report-batch2.json`, `fouc-frames/b2-dark-nocache-run3-frame3.png`).

**Options Considered**:

1. **Keep next-themes' script as the only initialiser.** No code is needed, but the observed flash stays. Rejected: 637.12 requires no flash of the wrong theme.
2. **`next/script` with `strategy="beforeInteractive"`.** This is the framework's API for early scripts. Rejected: in the App Router, inline `beforeInteractive` content is queued to `self.__next_s` and runs only when the client bootstrap starts (`next/dist/client/script.js`, `app-bootstrap.js`). That is after first paint, so it would not fix the flash.
3. **Move the provider so its script lands in `<head>`.** Rejected: `<AuthProvider>` wraps `<html>`, and a provider between `<html>` and `<body>` would render a `<script>` as a direct child of `<html>`. That is invalid markup, and React's hydration behaviour for it is not guaranteed.
4. **A server-rendered class from a cookie.** Rejected: ADR-371 and open question #5 store the preference in the browser (`localStorage`). A cookie preference is a different decision, out of this phase's scope.
5. **A parser-blocking inline `<script>` in the root layout's `<head>`, built from the same constants as the provider (chosen).**

**Decision**: Option 5.

- `frontend/components/theme/theme-config.ts` is the single source. It holds `THEME_STORAGE_KEY` (`kazi-theme`), `DEFAULT_THEME` (`light`), `THEMED_ROUTE_PREFIX` (`/org/`), the `isThemedRoute` predicate and `THEME_INIT_SCRIPT`. The script string is generated from those constants.
- `app/layout.tsx` renders `<head><script dangerouslySetInnerHTML={{ __html: THEME_INIT_SCRIPT }} /></head>` and stays a Server Component. `KaziThemeProvider` imports the same constants and predicate.
- The script applies exactly what the provider would: forced light unless the pathname starts with `/org/`, stored `light` or `dark`, `system` via `prefers-color-scheme`, otherwise light. It swaps the `dark`/`light` class and sets `style.colorScheme`, and it is wrapped in try/catch, including around `localStorage`.
- next-themes stays the runtime owner of the theme: the toggle, system changes, cross-tab sync and `forcedTheme`. Its own script still runs, and running it after the head script changes nothing.

**Rationale**:

- A `<script>` in `<head>` without `src`/`async`/`defer` blocks the parser before any `<body>` content exists, so no body paint can precede it. Run 2 of OBS at `4816cf440` confirms this: in all 35 throttled reloads (20 dark/no-cache, 10 light/no-cache, 5 dark/cached) the class was set while `document.body` was still `null`, and 0 runs showed the wrong theme (`qa_cycle/evidence/phase90-ui/637B/fouc-diag-report.json`, `head-check-report.json`).
- Duplicating next-themes' small init logic is contained and checked by tests. `frontend/__tests__/components/theme/theme-script.test.tsx` runs the generated script in happy-dom. It also server-renders the real `KaziThemeProvider`, extracts next-themes 0.4.6's own inline script, and asserts that both produce the same class and `colorScheme` across path, storage and OS-scheme combinations. A next-themes upgrade that changes its behaviour fails that test.
- React 19 does not hoist an inline script without `src`, and the root layout is hydrated, not client-created, so there is no "Encountered a script tag" warning. OBS recorded 0 such warnings and 0 hydration warnings. `suppressHydrationWarning` on `<html>` already covers the class and style change.

**Consequences**:

- Positive:
  - No wrong-theme first paint on slow or cold loads.
  - One module defines the theme constants for both the head script and the provider.
- Negative:
  - Two scripts initialise the theme (the head script, then next-themes'). The parity test is what keeps them aligned.
  - The app has no Content-Security-Policy today, so no nonce is needed. If a CSP is introduced, both this script and next-themes' script need a nonce or hash; next-themes accepts a `nonce` prop.
  - Edge differences until next-themes' script runs:
    - Garbage stored value: the head script applies `light`, then next-themes adds the garbage string as a class. Neither sets `dark`.
    - Throwing storage: the head script applies `light`, and next-themes sets nothing.
  - Both edge cases paint light.

**Related**: [ADR-371](ADR-371-dark-mode-light-default.md) (dark mode via next-themes, light default; this ADR refines its placement rationale), [architecture §15](../architecture/phase90-ui-modernization.md); slice 637B (`tasks/phase90-ui-modernization.md`), PR #1760.

````

````markdown
## 15.1 Overview

Phases 87–89 fixed Kazi's information architecture and then its correctness; the data model and API are sound, and Phase 89's exit work proved the trust engine end to end. The presentation layer was never designed as a system. Every in-scope page hand-builds its own header (94 inline `font-display text-3xl` h1s), its own table (48 files import `ui/table`, ≈53 contain a raw `<table`), its own cards (≈217 hand-rolled `rounded-* border` divs) and — almost nowhere — its own charts: three live chart usages, five dead chart components, and a `lib/chart-theme.ts` whose comments contradict its values. A `.dark` token block and ≈3,850 lines of `dark:` classes exist, but nothing has ever applied `.dark`, so none of it has been observed. To a managing partner in a design-partner demo, an app that looks assembled reads as a risky small vendor before they see the trust ledger.

This phase builds a thin design-system layer on shadcn/ui (new-york, Radix — founder decision 3: the admincn template's code is **translated**, never moved to Base UI) and moves the surfaces a firm sees first onto it: the app shell, the firm dashboard, matters and clients (list and detail), the trust dashboard and reports/profitability. It is a **visual phase**. Labels, tab names, routes, IA and `data-testid`s do not change; the matter and client lists keep every behaviour they have; capability-gated money stays gated and a redacted value renders as an intentional "—", never 0. The only behaviour changes are named and bounded: the additive DataTable capabilities (column visibility, CSV of visible rows, opt-in page size), two read-only aggregate endpoints for the two time series the backend does not serve (trust balance per month, fees billed vs collected per month — [ADR-372](../adr/ADR-372-read-only-chart-series-endpoints.md)), and one declared side-effect fix: the trust dashboard's reconciliation card stops reading a hard-coded `null` (`trust-accounting/actions.ts:126-127`) because it is re-sourced from `/api/dashboard/trust-position` (rulings §6).

Three design rules carry the phase. **Layering**: tokens live in `@b2mash/ui/styles/globals.css`; framework-agnostic presentational primitives (PageHeader, StatCard) live in `@b2mash/ui`; anything that knows about Next.js routing, URL state, capabilities, saved views or recharts lives in `frontend/components/` ([ADR-367](../adr/ADR-367-design-system-layering.md)). **Charts are honest**: one categorical palette validated for colour-vision deficiency in both themes, status colours reserved and always paired with an icon or label, every chart carrying an accessible name and a text alternative, every money chart filtered to and labelled with the firm's default currency ([ADR-370](../adr/ADR-370-chart-kit-and-palette.md)). **Dark mode is opt-in and observed**: light by default, a Light / Dark / System choice in the user menu, semantic tokens in place of `dark:` pairs on the surfaces this phase touches, and a written debt list for the long tail ([ADR-371](../adr/ADR-371-dark-mode-light-default.md)).

### 15.2.1 Design-system layer map ([ADR-367](../adr/ADR-367-design-system-layering.md))

| Layer | Lives in | Contains | Rule |
|---|---|---|---|
| L0 Tokens | `packages/ui/styles/globals.css` (shared), `frontend/app/globals.css` (app-only: sidebar tokens, `@custom-variant dark`, `--brand-color`) | colour (OKLCH), chart/status palettes, radius, elevation, density | the only place a colour value is written; components reference tokens, never hex or raw `slate-*` for surfaces |
| L1 Shared primitives | `packages/ui/src/*` (`@b2mash/ui`) | existing button, badge, card, input, label, separator, skeleton, `cn`; **new** `page-header`, `stat-card` | no Next.js imports, no hooks that read routing or capabilities, no recharts, no lucide; server-safe (no `"use client"` unless interactive); every file gets an `exports` entry + `src/index.ts` re-export |
| L2 App primitives | `frontend/components/{ui,data-table,charts,shell,shared,theme}` | shadcn CLI output (`ui/sidebar`, `ui/chart`, `ui/toggle-group`, `ui/scroll-area`, `ui/breadcrumb`), `DataTable`, chart kit, `DetailHero`, `ThemeToggle`, `EmptyState` (in place), `AppSidebar`, `AppHeader` | may use Next.js routing, URL state, `useCapabilities`, recharts; composes L1 |
| L3 Feature components | `frontend/components/{matters,clients,customers,projects,dashboard,trust,profitability}` | column definitions, widgets, header compositions, hero data mapping | compose L1/L2; no new visual vocabulary |
| L4 Pages | `frontend/app/(app)/org/[slug]/**` | data fetching (RSC), gating, composition | **"new page" rule**: a new or next-touched page uses `PageHeader` + `DataTable`/`Card` + the kit — no inline `font-display` h1, no raw `<table>`, no hex |

Why `EmptyState` stays at L2 in place: it has 48 importers and takes `icon` as a component reference that RSC callers pass server-side; moving it to `@b2mash/ui` would need every importer edited in one slice and a lucide dependency in the package (rulings §3.6). ADR-367 records the move as a later, mechanical PR when the portal wants it.

Why `StatCard` is in `@b2mash/ui` but its sparkline is not: the portal will want a balance tile later, and the tile itself is pure presentation. The sparkline belongs to the chart kit — `SparklineTrend` is one of its dependency-free SVG micro presets, held to the kit's token and accessibility contract ([ADR-370](../adr/ADR-370-chart-kit-and-palette.md)) — so `StatCard` takes `sparkline?: ReactNode` and the frontend passes `<SparklineTrend>`; `@b2mash/ui` gains no chart code and the portal bundle is unchanged.
````
