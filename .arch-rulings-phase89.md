## 2. Rulings per gap

### R-E1a — Section 35 trust reports (G88-F40)
- Wire `trustReportPackSeeder.seedForTenant(schemaName, clerkOrgId)` into **both** call sites immediately
  after `standardReportPackSeeder` (`TenantProvisioningService:237`, `PackReconciliationRunner:140`).
- Gate inside `doSeed` on `verticalProfile == "legal-za"` (the `LegalTariffSeeder` precedent). Module flag
  not consulted (the page already hides TRUST cards when `trust_accounting` is off).
- Bring the seeder onto the 625E shape: `packVersionGate.recordIfAbsent(PackType.REPORT, "trust-reports", "1", …)`
  on first install, `reconcileAppliedPack` + an (initially empty) `RECONCILE` list exactly like
  `StandardReportPackSeeder` — so future definition edits reach existing tenants by version bump. PACK_VERSION
  stays 1 in this phase (no definition content changes); existing tenants are seeded fresh by the boot-time
  runner because none carries `trust-reports` in `reportPackStatus`.
- Capability mismatch: the trust reports page requires **both** `VIEW_TRUST` and `FINANCIAL_VISIBILITY`; a
  member with only `VIEW_TRUST` sees a specific empty state ("Trust reports need financial visibility"), not
  the generic fetch error. The controller stays `FINANCIAL_VISIBILITY`. (Open question §14.12: whether
  TRUST-category reports should accept `VIEW_TRUST` alone.)
- Observation: reconcile branch = "runner log + the Keycloak tenant's trust reports page lists 7 cards";
  fresh-tenant branch = provisioning integration test + e2e `day-90-review.spec.ts:123` un-fixme'd.

### R-E1b — Interest-run approval surface (G88-F39) → ADR-362
- Backend unchanged except one additive field: `MyCapabilitiesResponse.memberId` (the id
  `RequestScopes.requireMemberId()` resolves) so the client can hide self-approval. No new states, no
  cancel/delete endpoint in this phase (open question).
- UI: the runs table gets an **Actions** column. DRAFT (not calculated) → "Continue" (manage-trust);
  DRAFT (calculated) → "Review & approve" (approve-trust-payment and `run.createdBy !== me`), else "Review";
  APPROVED → "Post" (manage-trust). Each opens `InterestRunWizard` on an existing run via a new
  `initialRun` prop (wizard loads `fetchInterestRunDetail(runId)` and jumps to the matching step); the
  wizard remains the single UI for the lifecycle. The creator sees "Awaiting approval by another member".
  Status badge via a label map (Draft / Approved / Posted), never the raw enum.
- Backend error "Self-approval not allowed" is still surfaced verbatim as the fallback.

### R-E1c — Client ledger running balance (G88-F23) → ADR-361
- **Backend is the single source.** `GET /api/trust-accounts/{accountId}/client-ledgers/{clientId}/history`
  rows gain `runningBalance` (nullable). Computed in a native query with a window function over **posted**
  rows only (`status IN ('RECORDED','APPROVED')`, type sets identical to `calculateClientBalanceAsOfDate`,
  `REVERSAL` type excluded) ordered `transaction_date, created_at, id`; the page is returned in the reverse of
  that order (`DESC, DESC, DESC`). Non-posted rows (`AWAITING_APPROVAL`, `REJECTED`, `REVERSED`) and
  `REVERSAL` rows carry `runningBalance = null` and render "—".
- Invariant (integration test): the first row's `runningBalance` equals `calculateClientBalanceAsOfDate(today)`
  after a deposit, a fee transfer and a refund; and equals the `/statement` endpoint's last
  `LedgerStatementLine.runningBalance`.
- Frontend: the card page deletes its backward walk and renders the field; both pages drop `REFUND` from
  `isInflowType` (colour/arrow only on the transactions page). The history query also binds the four filter
  params the UI already sends (`type`, `status`, `dateFrom`, `dateTo`) — same query, same slice.

### R-E3b — Payment receipt (G88-F32) → ADR-364
- **No new table.** One nullable column: `payment_events.receipt_generated_document_id uuid REFERENCES
  generated_documents(id)` (tenant V10 §1).
- New pack template `payment-receipt-za` (legal-za pack, `primaryEntityType INVOICE`, category **OTHER** —
  no new `TemplateCategory` value; a new enum value is a cross-layer change and nothing needs it). Resolved by
  key like the fee note (`findPackSeeded("legal-za", "payment-receipt-za")`). Letterhead block as the fee note.
- Context: `InvoiceContextBuilder` gains `invoice.amountPaid`, `invoice.balanceDue`, `invoice.paidAt`,
  `invoice.payments[]` (date, method label, amount, reference, balance after); the receipt's own payment goes
  in `extraContext` as `payment.{id, number, date, methodLabel, amount, reference, balanceAfter}`. Receipt
  number = `{invoiceNumber}/R{n}`, n = ordinal of the COMPLETED payment event by `created_at` (computed, not
  stored as a sequence).
- Trigger: `@TransactionalEventListener(AFTER_COMMIT)` on `InvoicePaidEvent` / `InvoicePartiallyPaidEvent`
  (both get an additive `payment_event_id` in `details`), REQUIRES_NEW, `saveToDocuments=false`, actor = the

  **Lazy fallback:** the download endpoints generate the receipt on first request if the FK is null.
- Portal: `GET /portal/invoices/{id}/payments` → `[{paymentEventId, date, methodLabel, amount, reference,
  receiptAvailable}]`; `GET /portal/invoices/{id}/payments/{paymentEventId}/receipt` → `PortalDownloadResponse`.
  "Download receipt" appears on PAID and PARTIALLY_PAID detail pages per payment row.
- Firm: `PaymentEventResponse` gains `receiptGeneratedDocumentId`; download via the existing
  `/api/generated-documents/{id}/download`; the invoice page's payments section shows the link.
- **Fee-note download fix:** `PortalReadModelService.getInvoiceDownloadUrl` filters to the resolved fee-note
  template id (never "latest INVOICE document"). Integration test: pay, then download → fee-note bytes.

### R-E4b — Portal deadline sync (§5b row 19) → ADR-363 (extends ADR-256)
- Four new records in the sealed `DomainEvent` permits list, published by `CourtCalendarService` and
  `PrescriptionTrackerService` (both gain `ApplicationEventPublisher`):
  `CourtDateScheduledEvent` (create; update when date/type/court changed; the **new** row of a postpone;
  outcome recorded → carries `status=HEARD`), `CourtDateCancelledEvent` (cancel; and the **original** row of a
  postpone), `PrescriptionDeadlineSetEvent` (create; update), `PrescriptionDeadlineClearedEvent` (interrupt).
- `DeadlinePortalSyncService` listeners: Scheduled → `upsertFromDeadline` (HEARD → `overrideStatus=COMPLETED`);
  Cancelled / Cleared → `deleteBySourceEntityAndId`. Row id = the firm-side entity id; `sourceEntity`
  `COURT_DATE` / `PRESCRIPTION_TRACKER`; `deadlineType` `COURT_DATE` / `PRESCRIPTION`.
- **Visibility rule:** every portal contact of the customer that owns the matter sees every court date and
  prescription on it. Owner = the entity's denormalised `customer_id` (`projects.customer_id`), fallback
  `customerProjectRepository.findFirstCustomerByProjectId`; no row when neither resolves. Co-clients on a
  multi-client matter do **not** see them (one row per deadline; PK `(source_entity, id)`).
- **Copy rule (sanitised):** court date label = humanised `date_type` + court name ("Hearing — Johannesburg
  High Court"); description = `court_reference` only; **never** judge/magistrate, outcome or free-text
  description. Prescription label = "Prescription deadline"; description = humanised `prescription_type`;
  never cause-of-action detail or interruption reason.
- **Backfill:** `PortalDeadlineBackfillRunner` (same runner pattern, marker `portal_deadline_backfill`):
  court dates `status IN (SCHEDULED, POSTPONED) AND scheduled_date >= today(SA)`; trackers not
  INTERRUPTED/EXPIRED with `prescription_date >= today(SA)`; via `upsertFromDeadline` (widen to public or put the
  runner in the same package). `FILING_SCHEDULE` stays dormant (ADR-330).
- No mark-read control (decision 7). Portal `/deadlines` already renders all four source types.

## 5. Amendment 2026-11-04 (after ADR writing) — backfill marker store

`portal.portal_contact_directory_backfill(tenant_schema PK, backfilled_at, row_count)` (global V2) has no
backfill-name column, so it cannot hold the task or deadline backfill markers. **Ruling:** one shared global
table **`portal.portal_backfill_markers(backfill_name varchar(64), tenant_schema varchar(63), backfilled_at
timestamptz, row_count int, PRIMARY KEY (backfill_name, tenant_schema))`** in **global V3**, used by both
`PortalTaskBackfillRunner` (`portal_task_backfill`) and `PortalDeadlineBackfillRunner`
(`portal_deadline_backfill`). The V2 directory table is left as is (not migrated into the new table — no
reason to touch a working marker). Global V3 ships with the first of the two backfill slices to merge (next
free at build time). Rulings §0 "Global: none planned" is superseded by this section.

## 6. Rulings on the consistency review (2026-11-04, after Step 3 review A)
