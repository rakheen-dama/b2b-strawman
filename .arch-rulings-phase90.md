## §2 Founder rulings taken during /architecture (2026-11-11)
- **R1 — Margin tile hidden.** `/api/dashboard/kpis` hard-codes `averageMarginPercent = null`. The KPI row ships **four** tiles: active matters, hours logged, billable %, overdue tasks. Do not compute margin this phase; it's a future ADR. Leave the backend `averageMarginPercent` field untouched.
- **R2 — KPI leak fixed by a standalone pre-phase PR.** `withFinancialsRedacted` does not redact `previousPeriod.billablePercent` (or `previousPeriod.averageMarginPercent`). Fix it as prerequisite **P1**, outside the phase:
  - its own PR, red test first;
  - full backend verify;
  - branch `fix/kpi-previous-period-redaction`.
  The KPI-row slice depends on P1 having merged. The doc records P1 under a "Prerequisite" heading, as Phase 89 did.
- **R3 — "Collected" means payments received.** Sum completed payment events, bucketed by payment date in SA time. Part-payments and trust-to-business fee transfers are included. "Billed" means invoice totals bucketed by issue date (approved/sent/paid; not draft, not voided — the doc names the exact status set after reading the `Invoice` status enum). Both amounts are filtered to the org's default currency, as `outstandingSummary` does. ADR-372 records this choice and the rejected `paid_at` alternative.
- **R4 — Founder decisions 1–7 from the requirements stand**: foundation + hero surfaces; evolve Signal Deck; template code may be adapted (translate Base UI → Radix); hero header + tabs; small read-only endpoints; dark mode light-by-default and opt-in; no portal restyle; no customizer.

## §3 Corrections to the requirements' scouting note (verified)
1. **The dashboard is audience-driven.** `lib/dashboard-home.ts` chooses one of three audiences (fee earner, firm, owner) from capabilities. Each has its own `AUDIENCE_ROWS`, pinned by `home-matrix.test.tsx`. Section 4's regrid ("today's work → money → risk → activity") is expressed as changes to each audience's rows. The audience model and capability selection do not change. The KPI row goes in the firm and owner audiences. For the fee-earner audience the doc decides: personal hours tile only, or no KPI row.
2. **KPI endpoint shape.**
   - Requires `from` and `to` (no granularity param). `trend` is a 6-period **hours-only** series ending at `to`, with gaps where nothing was logged.
   - `previousPeriod` is the equal-length window before `from`.
   - Active matters and overdue tasks are point-in-time counts, so their tiles show **no delta**.
   - Only the hours tile gets a sparkline. Billable % shows a delta and no sparkline.
   - Redaction is by admin/owner **role**, not capability. A null value renders "—" or the tile is hidden.
   - `date-range-selector.tsx` is used by My Work, not the dashboard. The dashboard KPI row uses a fixed period (decide: this month vs last month, or the last 30 days vs the 30 days before) with **no new selector**, unless the doc justifies reusing the selector.
3. **Lists have no pagination.** Pages fetch every row and do search and sort in the server component, with state in the URL (matters: `sort`/`dir`; clients: `sortBy`/`sortDir`). The tables are server components. The e2e helpers expect a matter's link to be visible without paging. The DataTable therefore defaults to **client-side mode with pagination off** (opt-in page size) and keeps the existing URL params and server-side sort. Server-paginated mode is designed in ADR-369 but not built unless a slice needs it. TanStack runs inside a client component that receives server-fetched rows. Columns, sort state and saved views stay URL-driven.
4. **Saved views** (`components/views/*`) integrate as documented in `.arch-context.md` §5–6. DataTable gives them a toolbar slot and must not change how they work.
5. **`GroupedTabBar`** (`components/shared/grouped-tab-bar.tsx`) drives **both** matter and client tabs, so one restyle slice covers both. The URL mechanics differ (matters use `history.replaceState`; clients use `router.replace`) and must be preserved as they are; unifying them is out of scope.
6. **EmptyState already exists** (`components/empty-state.tsx`, 48 importers). Restyle it in place, adapting `empty-state-v2`. Do not create a second one; do not move it to `@b2mash/ui` unless ADR-367 says so and every importer is updated in the same slice.
7. **The `TrustBalanceCard` "duplicate" is a 5-line deprecated re-export.** Delete it and repoint its one test import. This is trivial; fold it into the clients slice.
8. **Dead code to delete.** The chart files `horizontal-bar-chart`, `radial-gauge`, `kpi-card`, `sparkline-chart`, `sparkline`, plus the widgets `incomplete-profiles-widget` and `information-requests-widget`. Grep repo-wide again at build time. `chart-components.test.tsx` covers the live donut and stacked bar too, so **edit** it; don't delete it.
9. **No nav badges exist.** `NavItem` has no count field. Drop that requirement; adding counts would be a new feature.
10. **No committed visual baselines.** Batch F's compares are opt-in (`E2E_VISUAL=1`) and its baselines are local-only and excluded from Docker builds, so the phase has nothing to regenerate. The tracked docs PNGs (`documentation/screenshots/`, `frontend/public/screenshots/`) go stale: the exit slice either re-shoots them or lists them.
11. **User menu and theme.**
    - The user menu is two hand-rolled popovers: mock auth, and Keycloak (`user-menu-bff.tsx`). The theme toggle must be added to **both**. Converting them to a Radix `DropdownMenu` is allowed in the shell slice if `/architecture` judges it necessary for the toggle; otherwise add a toggle item to each.
    - `AuthProvider` wraps `<html>`, so the ThemeProvider goes inside `<body>`, and `<html>` gets `suppressHydrationWarning`.
    - `next-themes` is a new dependency; ADR-371 justifies it. It is the second new dependency after `@tanstack/react-table`.
12. **Portal impact.** 31 portal source files import `@b2mash/ui`. Any token or primitive change in `packages/ui` requires PORTAL-GATE. The portal's look may shift slightly; the doc must state that portal-visible changes are limited to token retunes, and that the portal does **not** get dark mode (no `.dark` class is ever applied there).
13. **Chart tokens.** `chart-1..5` are stock shadcn colours whose hue changes between light and dark. ADR-370 redefines them as a Kazi categorical palette that stays recognisable in both themes, adds sequential and status tokens, and makes `lib/chart-theme.ts` read CSS variables. Use the `dataviz` skill's method (form heuristic, colour validator) when the doc specifies the palette. The doc gives OKLCH values, or a method plus constraints that the token slice must pass.

## §5 The two new endpoints (rulings; the doc refines them)
Both endpoints are:
- additive and `GET`;
- tenant-scoped through the existing filter chain;
- `Clock`-injected (ADR-358);
- checked with the same capability and module checks as their siblings;
- computed from existing tables;
- free of migrations, entities, caches and writes;
- covered by an integration test modelled on `dashboard/TrustPositionIntegrationTest.java` (seed data through the REST endpoints, compare the aggregate against the individual reads, cover 403 and 404/empty).

1. **`GET /api/dashboard/trust-balance-trend?accountId={uuid?}&months={1..24, default 12}`**
   - Gate: VIEW_TRUST + trust module (the same gate as `trust-position`).
   - Returns month-end balances: an opening balance before the window, plus monthly net movements from `trust_transactions`, run as a cumulative sum.
   - Uses the **same sign and status rules as the existing balance queries** (name them).
   - Defaults to the primary account.
   - Month boundaries are in SA time.
2. **`GET /api/reports/billing-trend?months={1..24, default 12}`**
   - Gate: FINANCIAL_VISIBILITY (the same gate as the profitability report).
   - Returns per month: `billed` (invoice totals by issue date, statuses per R3) and `collected` (completed payment events by payment date, per R3), both in the default currency, with the currency code in the response.
- **Aged debtors: no new endpoint.** Use the existing 4 per-client buckets from `/debtors` (current, 1–30, 31–60, 61+) and sum them on the client for the widget if the widget needs firm totals. Keep the existing gate.
- The two endpoints may ship in **one** backend slice (one verify) or in the slice of the chart that consumes each. The doc chooses and justifies by verify cost. The target is at most 2 Java-touching slices, plus prerequisite P1 outside the phase.

## §6 Other behaviour notes
- **Trust dashboard.** `trust-accounting/actions.ts:126-127` hard-codes the last-reconciliation date and status to `null`. Moving the StatCards onto `/api/dashboard/trust-position` fixes this as a **declared side effect** of the Section 7 slice. The PR names it, adds a vitest test, and makes a real-browser observation. This is the one sanctioned behaviour change in a visual slice.
- **Utilization chart.** Non-admin users are limited to their own row by role, so a custom FINANCIAL_VISIBILITY role sees a one-bar chart. With fewer than 2 rows, render the table and a short note instead of a chart.
- **Mixed currency.** Every chart that sums money filters to, or labels, the default currency. No silent cross-currency sums.

## §7 Slicing (binding, by verify cost — memory `feedback_slice_by_verify_cost`)
- One PR per slice. ≈12–20 files and ≤ ~1500 new lines.
- Order: tokens/theme → shell → primitives → surfaces → gate. Surface slices depend on the primitives they use.
- Java-touching slices run the full `backend/scripts/verify.sh`: at most 2 inside the phase (the new endpoints), plus P1 outside.
- Frontend-only slices run FE-GATE. A slice that touches `packages/ui` also runs PORTAL-GATE. Every UI slice re-runs the legal Playwright suites (`legal-lifecycle`, `legal-depth-ii`) on a fresh stack before merge and records a real-browser observation at 1024 and 1440 in light and dark.
- Target roughly **8 epics / 15–19 slices**. Epic numbers continue from the highest in TASKS.md; the doc names them E1…E8, and `/breakdown` assigns real numbers.
- Branch convention: `phase90/<nn><slice-letter>-<slug>`.
