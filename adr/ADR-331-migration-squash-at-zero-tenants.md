# ADR-331: Migration Squash at Zero Tenants — V1 Baselines, `baselineOnMigrate(false)`, Parity Test, Irreversibility Rule

**Status**: Accepted

**Context**:

The tenant Flyway series runs to `V135` (133 files) and the global series to `V25` (25 files). Phase 86 deletes 18 entities and 21 tables, drops columns on five surviving tables, deletes migration-seeded rows (`org_role_capabilities` `RESOURCE_PLANNING`, V67), shrinks three CHECK value lists, and removes three global read-model tables (`architecture/phase86-subtraction-legal-only.md` §11.2, §11.7(g)). Under normal rules each deletion would be a `V136+` drop migration and the series would keep growing forever. The founder decision (`requirements/claude-code-prompt-phase86.md`, "Squash migrations inside this phase") is to regenerate both series as a single `V1__baseline.sql` each, inside this phase, from the post-removal schema — because **there are zero production tenants**. No trust ledger, fee note or client record exists outside developer volumes, so there is no data to migrate and `flyway_schema_history` can be discarded.

A second point where the requirements and the architecture disagree: the requirements say "no migration edits per slice — the squash deletes the tables". Review of the slice plan showed that deferring every DROP to the squash breaks slices 5–10: V67 seeds `'RESOURCE_PLANNING'` into `org_role_capabilities` for owner and admin, `OrgRole.capabilities` is `@Enumerated(STRING) Set<Capability>`, so deleting `Capability.RESOURCE_PLANNING` (slice 5) while the rows survive makes every owner/admin role load throw on every request via `MemberFilter`. The same deferral leaves `OrgSettingsSchemaSnapshotTest` (which reads `information_schema` from a Flyway-provisioned tenant) unable to shrink per slice, and would make the pre-squash parity snapshot contain dead tables. The architecture overrides (§11.3 intro, §11.3.10(j)): each removal slice ships its own throwaway drop migration and the squash collapses the whole series.

Every tenant lives in its own schema (ADR-064, Phase 13 dedicated-schema model), migrated by `provisioning/TenantMigrationRunner` and `TenantProvisioningService`, with the global `public`/`portal` schemas migrated by `config/FlywayConfig.globalFlyway`. Phase 75's shard-aware runner (inline ADRs 293–297 in [`architecture/phase75-scalability-job-queue-sharding.md`](../architecture/phase75-scalability-job-queue-sharding.md)) configures Flyway by location, not version, and is unaffected. Phase 84 (take-on) is already specced and references constraint names (`chk_trust_txn_type` etc.) by name; it is sequenced *after* this phase so its tables land as `V2` on a clean `V1`.

One point where the architecture doc and the requirements disagree: the requirements say `FlywayConfig`/`TenantMigrationRunner` should be updated "only if the baseline requires it (it should not)". Scouting found that it does — all three sites use `.baselineOnMigrate(true)` with the default `baselineVersion` of `1`, which after the squash would silently skip `V1__baseline.sql` on a non-empty, history-less schema (§11.7(c)). The doc wins; the change is recorded here.

**Options Considered**:

### A. Whether and when to squash

1. **Per-slice throwaway drop migrations, then squash inside Phase 86 as slice 11, after slices 2–10 are merged and `main` verify is clean (CHOSEN)** — each removal slice (2–10) ships a forward migration (tenant `V136`…`V142`, global `V26`…`V28`, numbered in merge order) that drops its tables, columns and migration-seeded rows and re-defines any shrunken CHECK (`invoice_lines_line_type_check`, `chk_email_delivery_reference_type`, `chk_dt_category`), so the live schema is code-consistent at every slice gate; slice 11 then regenerates one `V1__baseline.sql` per series from that schema and `git rm`s the old files **and** the drop files; Phase 84 becomes `V2`.
   - Pros: the only moment the squash is a pure file-count change is while no data exists; every slice is independently green (no deferred-DROP cascade — the `RESOURCE_PLANNING` row deletion lands with the enum deletion); `OrgSettingsSchemaSnapshotTest` shrinks per slice in the same PR; the end-of-slice-10 parity snapshot is the true post-removal schema, so byte-equal parity is meaningful; sequencing 86 → 87 → 84 means Phase 84's tables are the first feature migration on the baseline, and the Phase 84 spec's constraint-name references resolve against one readable file; removes ~168 files, 21 dead tables and every `V<NN>MigrationTest` that pins a file name.
   - Cons: ~10 migration files are written to live for at most nine PRs; every local, e2e and embedded-Postgres volume must be wiped once at slice 11 (`dev-down.sh --clean`, `e2e-down.sh`) — there is no reconciliation path; the migration history is readable only at `horizontal-platform-final` (ADR-330).
2. **Squash inside Phase 86 with no per-slice migrations** — slices 2–10 delete code only; slice 11 drops the tables by omitting them from the baseline (the requirements' literal reading).
   - Pros: fewest files written; one place to review all DDL.
   - Cons: **does not work** — `Capability.RESOURCE_PLANNING` cannot be deleted while V67's seeded rows exist (every owner/admin role load throws); `OrgSettingsSchemaSnapshotTest` cannot shrink until slice 11, so slices 2/4/5/6/10 are red or the pin is frozen with dead columns; the parity snapshot captured before the squash contains the dead tables, so the "byte-equal" proof compares the wrong schema; the only ways out are to gate the deletions on a flag (forbidden) or to skip the per-slice full verify (forbidden).
3. **Keep the full history permanently**; each removal slice adds a `V136+` drop migration and nothing is ever squashed.
   - Pros: no volume wipe; conventional.
   - Cons: a fresh tenant would still create and then drop 21 tables; 158 files plus ~10 drop files to carry forever; Phase 84 lands at ~`V143` with its named constraints scattered across a dozen files; the zero-tenant window closes at Phase 84 and never reopens — this is the one time the squash is free.
4. **Squash later as its own phase** (after Phase 87 or after Phase 84).
   - Pros: separates "delete" from "rewrite history" for review.
   - Cons: after Phase 84 the first design-partner firm's data exists and the squash becomes a data migration with the irreversibility rule already in force; after Phase 87 only, the gain is nil (87 renames the wire, not the schema) and the removal slices would still have written the same drop migrations — only the squash moves.
5. **No-op placeholder migrations** — keep `V1..V135` as empty files so existing volumes validate, put the real baseline at `V136`.
   - Pros: no volume wipe for developers.
   - Cons: 158 empty files is history theatre; a fresh tenant runs 158 no-ops before the baseline; Phase 84 becomes `V137`; Flyway's checksum validation still fails on volumes whose applied checksums differ from the emptied files, so the wipe is not actually avoided.

### B. How the baseline is generated

1. **Dump a freshly provisioned post-removal tenant (old series + slices 2–10's drop migrations applied), hand-clean into deterministic DDL, prove parity (CHOSEN)** — `pg_dump --schema-only --no-owner --no-privileges --no-comments` per schema plus data-only dumps of migration-seeded rows (`org_roles` + `org_role_capabilities`, counters, `shedlock`, `shard_config`); strip `SET`/`search_path`/`OWNER`/`COMMENT`; unqualified names; FK-dependency order; every `chk_*`/`uq_*`/`idx_*`/`fk_*` name verbatim; `org_roles` system rows kept as V67's `gen_random_uuid()` inserts + `INSERT … SELECT … WHERE slug =` capability grants, never as literal UUIDs; header block naming the commit and the tag (§11.7(a),(h)).
   - Pros: the live schema is the only authoritative description of what 133 files plus the drop migrations actually produce; because the drops ran per slice, the schema at the end of slice 10 already matches the code, and `BaselineSchemaParityTest` compares `information_schema` + `pg_indexes` byte-equal to a snapshot committed at that point, so the hand-cleaning is verifiable rather than trusted.
   - Cons: hand-cleaning is manual and the parity snapshot must be captured *before* the squash or there is nothing to compare against; seeder-written rows (packs, templates, tariffs) are deliberately excluded and must keep running on every provision.
2. **Hand-merge the 158 files** into one.
   - Pros: no database needed; diffs read as edits to known files.
   - Cons: the removal PRs change what the series produces, so a hand merge is a second, unverified reimplementation of 133 files' worth of `ALTER`s; no mechanical proof of equality.
3. **Generate from Hibernate (`hbm2ddl`) off the entity model.**
   - Pros: entities are already the source of truth for columns.
   - Cons: entities do not carry the named CHECK constraints, partial indexes, JSONB default literals (V117's `portal_notification_doc_types` allowlist) or the migration-seeded rows Phase 84 depends on; `ddl-auto` cannot see per-tenant schemas, which is why the test profile keeps it `none`.

### C. `baselineOnMigrate` after the squash

1. **`.baselineOnMigrate(false)` at all three production sites (CHOSEN)** — `FlywayConfig.globalFlyway`, `TenantMigrationRunner.migrateSchema`, `TenantProvisioningService:276-282` — and at the two test-only Flyway builders (`ShardIsolationTest:108`, `EndToEndMultiShardTest:119`) so the tests mirror production.
   - Pros: Kazi never migrates a pre-existing schema — tenant schemas are created empty and `public` on a fresh database is empty — so a non-empty schema without a history table is always operator error and must fail fast (`FlywayException: Found non-empty schema(s) … without schema history table`).
   - Cons: a managed Postgres host that pre-populates `public` would fail the global migrate (documented fallback: `.baselineOnMigrate(true).baselineVersion("0")` on the global site only).
2. **Leave `baselineOnMigrate(true)` with the default `baselineVersion` (`1`).**
   - Pros: no code change; matches the requirements' expectation.
   - Cons: on a non-empty, history-less schema Flyway baselines at `1` — now equal to the baseline file's version — and silently skips `V1__baseline.sql`, leaving a schema with no Kazi tables and a history row claiming otherwise. Under the old series the same event failed loudly at `V2`.
3. **`baselineOnMigrate(true).baselineVersion("0")` everywhere.**
   - Pros: still applies `V1` on a history-less schema.
   - Cons: papers over a tenant schema that somehow has tables but no history — which should never happen and should not be tolerated silently.

**Decision**: Per-slice throwaway drop migrations in slices 2–10, then squash inside Phase 86 as slice 11 (A1), generating both baselines by dump-and-clean from the end-of-slice-10 schema with a byte-equal parity test (B1), and switch all three production Flyway sites plus the two test-only builders to `.baselineOnMigrate(false)` (C1). No existing migration file is ever edited; the drop migrations are new forward files that exist only until the squash. `backend/db/BASELINE.md` records the squash commit, the archive tag, the generation steps and **the rule**: once the first production tenant exists (Phase 84 take-on), the baseline is immutable, nothing is ever squashed again, and every schema change is a new `V<n>__` file. The rule is enforced by convention and the PR template; there is nothing to enforce it against until Phase 84.

**Rationale**:

1. **Zero tenants is a one-time fact with an expiry date.** The window closes the day Phase 84 lands a firm's trust ledger. Everything the squash does — drop tables outright, discard `flyway_schema_history`, wipe volumes — is reckless with data and free without it.
2. **Schema-per-tenant (ADR-064) multiplies the cost of history.** Every tenant provision and every `@SpringBootTest` context replays the full series; the suite's cost is dominated by context builds and per-tenant provisioning (125+ migrations + seeders per context). One file per series is the cheapest possible provision.
3. **Phase 84 needs names, not history.** The take-on spec references `chk_*` constraints by name. One readable baseline with every name preserved verbatim, plus a parity test that proves nothing was lost, serves that better than 158 files.
4. **Fail-fast over silent skip.** `baselineOnMigrate(true)` was harmless when `V1` created one table; after the squash it is a latent data-loss hazard. The requirements allowed the change "if the baseline requires it", and it does.
5. **Every slice must be green on its own, and the schema must match the code at every gate.** A deferred DROP is a hidden dependency between PRs: the seeded `RESOURCE_PLANNING` rows prove that deleting an enum constant without deleting its rows is a runtime failure, not a cosmetic drift. Writing ~10 migrations that live for nine PRs is the cheap price for independently verifiable slices and a parity snapshot that is actually the post-removal schema. The requirements' "no migration edits per slice" is honoured in its intent — no *existing* file is edited — and overridden in its letter.

**Consequences**:

- Positive: tenant and global series are one file each; Phase 84 is `V2`; ~168 files (133 + 25 + the ~10 throwaway drops), 21 tables, 5 PayFast columns and 5 `org_settings` columns are gone from every fresh provision; `OrgSettingsSchemaSnapshotTest`'s column set must be untouched by slice 11 (the pin already shrank in slices 2/4/5/6/10, each in the same PR as the drop) — if the squash adds or removes a column, the baseline is wrong; an ordering-only re-pin is permitted if the baseline's `CREATE TABLE` column order differs from the accreted `ALTER TABLE` order (§11.7(e),(f)).
- Positive: slices 2–10 are each independently green and code-consistent — the drop migrations run in every `@SpringBootTest` context from the slice's PR onward, so a missed `DROP`/`DELETE` surfaces as an entity-load or `information_schema` failure in that PR's full verify, never later.
- Positive: `BaselineSchemaParityTest` is the concrete form of the "Hibernate schema validation" the requirements asked for, and asserts exactly one `flyway_schema_history` row (`version = '1'`) per schema.
- Negative: migration history is lost from `main`; the only way to read how a table evolved is `git show horizontal-platform-final:<path>` (ADR-330).
- Negative: **every** local, dev, e2e and `spring-boot:test-run` volume is wiped once after the squash commit; the root `CLAUDE.md` quick start and the PR description carry the instruction. Developers who skip it get "Detected applied migration not resolved locally" for V2…V142. (During slices 2–10 no wipe is needed — the drops are ordinary forward migrations.)
- Negative: ~10 throwaway migration files are written and reviewed only to be deleted; two open PRs can claim the same `V<n>` and must renumber on rebase (the parallel slice 8 global migration is the likely collision).
- Negative: eight `V<NN>MigrationTest` classes are renamed `*SchemaTest`; `V30`/`V31`/`V120` migration tests and `ProposalExpiredEmailIntegrationTest` (pinned to version `119`) are deleted; five main-code comments citing V-numbers are reworded.
- Negative: the irreversibility rule is a convention, not a check. After Phase 84 a careless squash would corrupt real tenants; `BASELINE.md`, the baseline header block and the PR template are the only guards.
