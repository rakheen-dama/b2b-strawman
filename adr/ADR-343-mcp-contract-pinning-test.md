# ADR-343: MCP Contract Pinning — `McpToolContractTest` Snapshots Every `@McpTool` Name, Description and Input Schema (and the Three Resources) to a Committed Resource; the Wire Rename Stops at `mcp/`

**Status**: Accepted

**Context**:

The `kazi-legal-za` plugin (`../claude-for-legal-sa`, seven SA-legal skills) is built on the Phase 78/81/82 MCP server and is the product's only conversational AI surface ([ADR-333](ADR-333-mcp-sole-conversational-ai-surface.md)). Phase 87 renames `project→matter` and `customer→client` on every REST path and DTO ([ADR-337](ADR-337-wire-rename-two-nouns-entities-stay.md)) — the exact nouns the MCP tool parameters and DTOs carry — and the requirements state that "MCP tools, schemas and the `kazi-legal-za` plugin contract are untouched; add a contract test if none exists that pins tool names and input schemas". Facts at HEAD `41cb211fb` (`.arch-context.md` §3.1, §8):

- **21 `@McpTool` methods** (`org.springframework.ai.mcp.annotation.McpTool` / `@McpToolParam`, Spring AI 2.0.0-M6 via `spring-ai-starter-mcp-server-webmvc`) in `mcp/tool/{McpPingTool, MatterTools, ClientTools, CorrespondenceReadTools, CorrespondenceWriteTools, TrustTools, BillingTools, ComplianceTools, DocumentTools, ActivityTools, AuditTools}`: `attach_document, file_correspondence, get_audit_events, get_client, get_correspondence, get_document_url, get_invoice, get_matter, get_matter_activity, get_trust_balance, get_unbilled_time, kazi_ping, list_clients, list_compliance_gaps, list_correspondence, list_invoices, list_matters, list_trust_transactions, propose_task, resolve_matter_by_email, search_documents`.
- Three resources: `kazi://matter/{id}`, `kazi://client/{id}`, `kazi://firm-profile` (`MatterResource`, `ClientResource`, `FirmProfileResource`).
- `mcp/dto/*` carries **`customerId` on the wire** (`McpMatterDto(… customerId …)`, `McpMatterListItem`, `McpInvoiceDto(… customerId, customerName)`, `McpTrustBalanceDto(trustAccountId, customerId, …)`); tool parameters use `projectId`/`customerId` (39/54 occurrences) beside 18 `matterId` / 3 `clientId`. The plugin's skills reference these names.
- Input schemas are **generated by Spring AI** from `@McpToolParam(required, description)` and the Java parameter types; they are code-defined and name-versioned by design ([ADR-306](ADR-306-mcp-tool-contract-design.md)), with no schema file in the repo.
- Existing tests: `McpReadOnlyRegistryTest` reflects over `m.getAnnotation(McpTool.class)` (line 237) and enforces **allowlists** — `WRITE_TOOL_NAMES = {file_correspondence, attach_document, propose_task}`, `READ_NAME_EXEMPTIONS = {resolve_matter_by_email}`, `PROBE_TOOL_NAMES = {kazi_ping}`, `ALLOWED_TOOL_BEANS`, `ALLOWED_WRITE_TOOL_BEANS`, the mutating-verb rule, and `initializeDoesNotAdvertisePromptsOrSamplingOrCompletion`. `McpHandshakeIntegrationTest` drives `initialize` + `tools/list` + `resources/list` over JSON-RPC but asserts only that the arrays exist and contain `kazi_ping`. Behavioural tests cover each tool's output. **No test pins an input schema, a description, or the full tool-name set.**
- `src/test/resources/` holds `ai/`, `fixtures/`, `schema/`, `META-INF/`, `application-test.yml`, `archunit.properties` — no `mcp/` directory yet.

A rename that touched `mcp/dto` or an `@McpToolParam` name would compile, pass every behavioural test, and break the plugin at the first `list_matters` call — the gap is a missing test, not a missing rule.

**Options Considered**:

1. **Rely on `McpReadOnlyRegistryTest`'s name allowlists only.**
   - Pros:
     - Already exists; blocks a *new* tool and any name outside the allowlists.
   - Cons:
     - It pins categories, not the contract: `customerId → clientId` on `McpMatterDto`, a renamed `@McpToolParam`, a changed `required` flag or a reworded description pass unnoticed.
     - A deleted tool whose name was in no allowlist passes too.
     - Its purpose (read-only structure, write-tool sanction) is orthogonal to "what does the plugin see".
2. **Snapshot test — `McpToolContractTest` serialises every tool's name, description and input JSON schema plus the resource list, as served by `tools/list` / `resources/list`, to a committed resource and fails on any diff (CHOSEN)** — the test drives the real JSON-RPC `initialize` → `tools/list` → `resources/list` over MockMvc (the `McpHandshakeIntegrationTest` path, so the snapshot is exactly what the plugin receives, including Spring AI's generated schemas), canonicalises the JSON (tools sorted by name, keys sorted, pretty-printed), and compares it byte-for-byte to `src/test/resources/mcp/tool-contract.json`. On mismatch it fails with a unified diff and the update instruction. Running with `-Dmcp.contract.update=true` rewrites the file; the rewritten file is reviewed in the PR like any contract change.
   - Pros:
     - Pins the whole observable contract — 21 names, descriptions, parameter names, types, `required`, pagination caps in descriptions, the three resource URIs — in one reviewable JSON file.
     - Any drift is a red PR with a readable diff.
     - Captures Spring AI's actual schema generation rather than re-deriving it by reflection, so a Spring AI milestone upgrade that changes schema output (`additionalProperties`, enum rendering, ordering) is caught — which is correct, because the plugin would see it too.
     - Updating is deliberate (`-Dmcp.contract.update=true`) and leaves a diff for CodeRabbit / the review gate to re-verify (CLAUDE.md §2).
   - Cons:
     - Descriptions become test-pinned.
     - A typo fix is a contract update (cheap, but a PR step).
     - Canonicalisation must be stable across JVM/Jackson versions (sorted keys, no map-order dependence) or the test flakes.
     - One `@SpringBootTest` context more in a suite already sensitive to context-cache keys (`backend/CLAUDE.md` rule 7 — reuse `McpHandshakeIntegrationTest`'s configuration, add no new property overrides).
     - Pins the server contract only; whether the plugin's prompts still *use* each tool correctly is the plugin repo's concern.
3. **Full OpenAPI-style spec generation for MCP.**
   - Pros:
     - Human-readable documentation of the contract.
     - Could be published to plugin authors.
   - Cons:
     - There is no springdoc in the backend (0 hits) and MCP is JSON-RPC, not OpenAPI.
     - A generated document without a diff gate is documentation, not a test.
     - Building a generator is a feature in an IA phase.
4. **Consumer-side test in the `kazi-legal-za` plugin only.**
   - Pros:
     - Tests the contract from the consumer's side — the only test that proves the plugin works.
   - Cons:
     - Lives in a separate repo, needs a running Kazi with OAuth and a tenant (the plugin's own GA gate still awaits a live OAuth round-trip); cannot block a Kazi PR; the merge-gate hook can only run tests in this repo.
     - Finds a break after the break is merged.

**Decision**: Option 2 — add `McpToolContractTest` in slice S1 (with the wire contract tests), snapshotting `tools/list` + `resources/list` as served to `src/test/resources/mcp/tool-contract.json`, failing on any diff and updating only via `-Dmcp.contract.update=true`; the `project→matter` / `customer→client` rename explicitly excludes the `mcp/` package, its DTOs and tool parameter names.

**Rationale**:

1. **The plugin is a dependency with no compile-time link.** Nothing in this repo fails to compile when `McpMatterDto.customerId` is renamed; only the snapshot can. Landing it in S1, before any rename batch, means the first rename PR that strays into `mcp/` is red at PR time.
2. **Serve, don't re-derive.** The schema the plugin sees is produced by Spring AI from annotations; a reflection-based test would reimplement the generator and drift from it. Driving the real `tools/list` makes the snapshot the contract by definition, and `McpHandshakeIntegrationTest` already shows how.
3. **Complements, does not replace, `McpReadOnlyRegistryTest`.** The registry test answers "is this tool allowed to exist and is it read-only"; the contract test answers "is what the plugin sees unchanged". Both run in the full verify; neither needs the other's allowlists.
4. **Deliberate updates match the quality gates.** CLAUDE.md §2 requires a review that re-verifies substantive claims; a committed JSON diff is the most reviewable form a contract change can take. The update flag makes "I regenerated the snapshot" an explicit, visible act rather than a side effect of a test run.
5. **`mcp/` is the boundary, in code and in the contract test.** [ADR-337](ADR-337-wire-rename-two-nouns-entities-stay.md)'s `WireVocabularyContractTest` excludes `/mcp` paths and the DTO scan excludes the `mcp/` package; this test pins the inside of that boundary. Together they state the rule once in each direction.

**Consequences**:

- Positive:
  - `backend/src/test/resources/mcp/tool-contract.json` is the committed, reviewable statement of the MCP contract (21 tools + 3 resources).
  - Any PR that changes it shows the diff.
  - The S1 rename PR proves the boundary: the snapshot is unchanged after `project→matter` lands everywhere else.
  - `mcp/dto/*`, `@McpToolParam` names and descriptions, resource URIs and the pagination caps stay as shipped to the plugin.
  - `McpReadOnlyRegistryTest` allowlists untouched.
  - A Spring AI upgrade that alters generated schemas is surfaced as a contract diff for a conscious decision rather than discovered by a plugin user.
- Negative:
  - Every future MCP change — including a description tweak — requires regenerating the snapshot with the flag and reviewing the diff; this is intended friction.
  - One more `@SpringBootTest` in the `mcp/` test package (29 entries today).
  - It must reuse the handshake test's context configuration to avoid a new context-cache key.
  - The test does not verify the plugin's behaviour, only the server contract.
  - A plugin-side live check remains a separate, manual GA gate.
  - Audit `entityType` values returned by `get_audit_events` / `get_matter_activity` are part of the observed contract only insofar as descriptions mention them.
  - The values themselves are protected by [ADR-342](ADR-342-audit-and-entity-tag-strings-stable-under-renamed-wire.md), not this snapshot.
- Follow-ups:
  - If the plugin repo later gains an automated contract check, point it at the same `tool-contract.json` (publish it as a build artefact) so both sides pin one file.
