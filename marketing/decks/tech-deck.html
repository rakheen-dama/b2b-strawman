Architecture

Deliberately boring choices, executed deeply

Frontend + portal

Next.js 16 · React 19 · TypeScript · Tailwind v4 · Shadcn — app shell and a separate client portal.

Backend

Spring Boot 4 · Java 25 · Maven. Gateway BFF in front, Keycloak OIDC (orgs, RBAC).

Data

PostgreSQL 16, schema-per-tenant via Hibernate + Flyway. S3 for documents.

Repo

pnpm workspace monorepo — frontend, portal, backend, shared UI/domain packages, infra.

Isolation

Schema-per-tenant, all the way down

  • One Postgres schema per firm — a trust ledger is the last place you want a missing WHERE clause.
  • Tenant context on Java 25 ScopedValue — structured, immutable, virtual-thread-friendly. Not ThreadLocal.
  • Flyway migrates every tenant schema; provisioning a firm is an API call.
  • Trade-off owned: migration fan-out cost vs. blast-radius containment. For compliance-heavy verticals, isolation wins.
Product thesis

Horizontal platform, vertical forks

  • The foundation is horizontal: projects, customers, time, billing, documents, audit, portal.
  • Verticals are profile packs — terminology, modules, templates, compliance packs (legal-za: trust accounting, FICA, court calendar; accounting-za; consulting-za).
  • A module registry + capability-based RBAC gate vertical surface per tenant.
  • Legal was picked as lighthouse because it's the hardest — surviving statutory trust accounting validates the foundation for every easier fork.
The new part

An MCP server over the practice

  • A firm's staff point their own Claude at their practice data — OAuth + per-firm POPIA consent, read-only by default.
  • Distributed skill pack (kazi-legal-za): fee-note drafting, s86 trust screening, FICA gap review, email filing, intake triage.
  • Write-back is gated: the AI proposes, a human approves inside the app — a first-class "AI gate" entity, fully audited.
  • Same service layer + read-model as the UI. No parallel data path. No prompt-injected SQL.
Process

An agent fleet with a constitution

/ideate→/architecture→/breakdown→/phase→/epic
  • Conversation → requirements → ADRs → epics → merged PRs, each step a versioned skill in the repo.
  • Each epic: an agent in an isolated git worktree; scout → builder pipelines; the orchestrator owns merges.
  • Every agent-authored PR passes independent review gates before merge.
  • The dev process itself is code-reviewed.
The hard problem

Keeping an agent fleet honest

  • Full mvnw verify + full frontend suite before merge — targeted tests never gate a merge.
  • "PASS means observed" — QA agents drive a real browser against a real stack. Inferring pass from "code looks right" is forbidden.
  • Reproduce-before-fix — no fix without a local repro. The spec might be wrong; the bug isn't.
  • A merge-gate hook physically blocks gh pr merge unless the bar is met.
  • Every correction becomes a standing rule in a lessons file. The ruleset is the asset.
War stories

What the process caught

The "green" that wasn't

Agents ran same-package tests only; a test elsewhere broke. Rule since: full verify or it didn't happen.

PASS by vibes

Agents claimed PASS on behaviour nobody observed. Rule since: browser-observed evidence or it's DEFERRED.

Debt-register landmines

Recorded "known fixes" that would have broken prod. Rule since: register entries are hypotheses until reproduced.

Agent throughput is easy. Agent trust is the engineering problem.
