## Root cause

- **HF-7:** `findUnmatchedCandidates` returns every posted unlinked row, and the tier 2–4 list (after 652H D-6) excluded only `REVERSED` rows. A `REVERSAL` contra therefore stayed a candidate at amount/date tiers for any line of its amount and sign.
- **M-1:** `withAutoMatchableReversedOriginalsOnly` decides shadowing only from the unlinked pool. A live re-entry G that is already linked is invisible, so R is unshadowed and takes a line by its old reference at tier 1.

## Rules implemented (`TrustReconciliationService`)

- **(b) The pair rule.** A member of a reversed pair matches only at tier 1 (its own reference and amount); it is never matched or suggested at tiers 2–4. A pair member is a REVERSED original or a `REVERSAL` contra; the check is the new `isReversalPairMember`.
  - **Pair members still count at tiers 2 and 3** (review fix, see below). Tier 2 (amount + exact date) and tier 3 (amount ± 3 days, 0.60) count candidates over the full sign-filtered list, pair members included, and act only when there is exactly one candidate and it is not a pair member. So a pair member keeps an otherwise-unique row ambiguous, as before FU-16, and is never picked itself.
  - **Tier 4 (amount only, 0.40)** links no row and keeps its existing "any match" rule, evaluated over the non-pair rows only, exactly as at 1d33d51 and as D-6 did for REVERSED originals. This deviates from the literal review ruling ("exactly one and not a pair member" for tiers 2–4), for two reasons:
    - "exactly one" would change live-row behaviour pinned by `TrustReconciliationServiceMatchingTest.autoMatch_amountOnlyMultipleCandidates_confidence040StaysUnmatched` (two live rows → 0.40);
    - counting pair members there would re-add a 0.40 hint for a reversed-only or contra-only amount, which `autoMatch_doesNotLetAReversedOriginalAbsorbAnUnrelatedLineByAmountAndDate` (D-6) and the HF-7 tests pin as null.
    - Tier 4 picks nothing, so there is no ambiguity to guard.
  - Confidences and lock order are unchanged. Tier 3 now returns its unique row (`amountCloseDateMatch`) and the caller writes the suggestion (`suggest`), with the same values as before.
  - **"Its own line" for a contra** is the line carrying the contra's reference. That reference is `REV-` + the original's reference, generated by `TrustPostingService.contraDraft` / `reversalReference`.
  - Why: this is the only signal that ties a bank line to a specific reversal. It is how the exit month's #8 (`REV-DEP-B-002`) and #10 (`REV-PAY-A-002`) match. It mirrors D-6 for originals and follows 652H found.md's guidance ("pair members auto-match only on an exact reference; never at tier 2 or 3").
  - Amount and date alone cannot tell the contra's own return from an unrelated movement, which is exactly HF-7.
- **(a) The shadow rule.** A REVERSED original is also shadowed by a live (non-REVERSED) row of its amount and cashbook sign that is already linked to a line, within the run's window (statement period ±7 days, same account).
  - **One read, split in memory** (review fix). `TrustTransactionRepository.findPostedInAutoMatchWindow` returns every posted row of the account in the window, linked or not. The caller partitions it: unlinked rows are the candidates; linked non-REVERSED rows are the shadows.
    - The candidate half has exactly the semantics of the old `findUnmatchedCandidates`: posted, `bank_statement_line_id IS NULL`, same account and window.
    - Posted rows are only RECORDED, APPROVED or REVERSED (`chk_trust_txn_posting`), so the in-memory `!REVERSED` equals the old SQL `status <> 'REVERSED'`.
    - Both old queries (`findUnmatchedCandidates`, `findLinkedLiveRows`) are removed; neither had another caller.
    - It is still a plain read with no lock.
  - CF-3 lock order is unchanged: lines are locked first, rows are locked in id order and the statement last. Matches are still decided before any row lock.
  - Contras still count as live rows for shadowing, as before.

## Residual risk

1. **Behaviour change (fails safe).** A contra's own return line that does NOT carry the contra's `REV-` reference used to auto-match at tier 2; it is now left UNMATCHED for manual match. Manual match is unchanged and accepts the contra; G4 keeps the month open until it is resolved. A firm whose bank prints its own reference on returns will match those by hand.
2. **Over-shadowing (fails safe, same class as the accepted 652H D-6a).** A live row of R's amount and sign that is linked in the window but unrelated to R now also pushes R off its own line. That line stays UNMATCHED for a human.
3. **Not addressed (out of scope):**
   - F-652H-1: `INV_INTEREST` residual R-1.
   - The unrecord contra of a statement-only row can still match a line carrying `REV-<its reference>` at tier 1. That is implausible, because such a line would be the bank reporting that return.
   - Part (c), F-652H-2.

## Review fixes (independent Opus review of #1834 @1d33d51; coordinator rulings)

### 1. Tier 2–4 ambiguity guard: regression introduced at 1d33d51, fixed
- **Scenario:** contra C (−1 000, 3 Mar) and an unrelated booked payment P (−1 000, 3 Mar, its own reference). The bank shows the return on 3 Mar under the bank's reference, and P on 4 Mar under P's reference.
  - The dates force the return line first: auto-match orders lines by date, then id. So the test is deterministic, whatever the UUIDs.
- **At 1d33d51:** tier 2 for the return line saw {P} alone and AUTO_MATCHED it to P at 0.80, leaving P's own line unmatched. This was RED: `red-ambiguity.txt`, full output in `red-ambiguity-raw.txt`.
- **Fix and test:** `autoMatch_aContraStillMakesTheAmountAndDateTiersAmbiguous_soTheReturnLineDoesNotTakeAPayment` is now green.
  - Tier 2 sees {C, P}, which is ambiguous; tier 3 is likewise ambiguous. The return line stays UNMATCHED with no row. By the code, tier 4 then sets a 0.40 hint from the live P, the same as on main; the test does not assert the confidence.
  - P's line then takes P by reference. A manual match of the return to C balances the month.
- **REVERSED originals behave as at 1d33d51 and D-6 (reasoned).**
  - A REVERSED original stays in the pool only if no non-REVERSED row of its amount and sign is in the initial pool or linked; contras count here. The pool never gains rows during a run.
  - So for a line of a kept original's amount and sign, the only candidates at tiers 2–3 are REVERSED rows. The result is one pair member or several, and either way no action, exactly as the old live-only list (empty) gave.
  - For lines of other amounts, the original never passes the amount filter.
  - All 14 pre-existing 652H tests stay green with identical assertions.
- **Exit month:** the 12 matches on G are all tier 1 by reference, untouched by tiers 2–4. The reasoning above is unchanged; E2E-LEGAL is the orchestrator's to run.

### 2. Race between the two reads: fixed
- A concurrent unmatch committing between the old `findUnmatchedCandidates` and `findLinkedLiveRows` could drop a row from both, leaving a REVERSED original unshadowed for that run.
- There is now one query, split in memory; see the (a) rule above.
- The fold does not change the candidate semantics, so the two-query design is not kept.
- CF-3 lock order is unchanged: lines locked first, then planned rows in id order, then the statement. The window read is a plain read between steps 1 and 2, as before.
- This one is not reproduced by a test: it needs a commit interleaved between two reads in one transaction. The fix removes the window structurally.

### Broader root cause, still present without pair members (follow-up candidate, not fixed)
- Auto-match runs all four tiers line by line, in date-then-id order. Tier 1 is not run across every line before tiers 2–4.
- So an earlier line with no reference match can take a row at tier 2 (amount + exact date) that a later line would have matched exactly by reference.
- **Observed** with a temporary probe (not committed; output in `probe-tier1-not-first.txt`). There are no pair members at all: payment P (−1 000, 3 Mar), an unrelated −1 000 debit on 3 Mar under the bank's reference, and P's own line on 4 Mar under P's reference.
  - The unrelated line AUTO_MATCHED P at 0.80.
  - P's own line was left UNMATCHED.
- The same behaviour is on main; FU-16 neither causes nor fixes it.
- Suggested fix: two passes. Run tier 1 for every line first, then tiers 2–4 for the lines still unmatched. Re-check §16.9.6 and the CF-3 plan-then-lock order when doing it.

### Minor 2: stale persisted suggestions — facts first

**How a suggestion is stored.** `bank_statement_lines` has `trust_transaction_id` (FK to `trust_transactions`) and `match_confidence` (`numeric(3,2)`, checked 0..1) (`V1__baseline.sql:1783-1787`; `BankStatementLine.java:47-50`). The same two columns carry a link and a suggestion; `match_status` tells them apart.

| `match_status` | `trust_transaction_id` | `match_confidence` | Meaning |
|---|---|---|---|
| AUTO_MATCHED | set | 1.00 / 0.80 | link (`applyAutoMatch`) |
| MANUALLY_MATCHED | set | 1 | link (`manualMatch`) |
| RECORDED | the primary created row | null | link (`StatementLines.markRecorded`) |
| UNMATCHED | the suggested row | 0.60 | tier 3 suggestion (`TrustReconciliationService.suggest`; before 3298250, `tryAmountCloseDateMatch`) |
| UNMATCHED | unchanged | 0.40 | tier 4 hint; sets confidence only, no row (`tryAmountOnlyMatch`) |

**Clearing before this fix.**
- Only unmatch clears these fields: `releaseMatch` for matched lines, `StatementLinePostingService:377-378` for recorded lines.
- No code path cleared an UNMATCHED line's suggestion. An old suggestion lasted until the line was matched, recorded or excluded, through any number of auto-match runs.
- When a line has no sign-compatible candidate, the old code hit an early `continue` before any tier ran.

**A suggestion is not a link.**
- `suggest` / `tryAmountOnlyMatch` write only the line. The suggested row's `bank_statement_line_id` is untouched, so the row stays in the unmatched pool and in the outstanding items.
- Only `applyAutoMatch` → `postingService.linkBankLine`, `manualMatch`, and record-from-line link a row.
- Pinned by `autoMatch_clearsAStaleSuggestionOfAContraOnAnUnmatchedLine` ("a suggestion was never a link") and `autoMatch_rewritesAStillValidSuggestionIdentically` ("a suggestion is not a link").

**Readers** (backend `git grep` of `getTrustTransactionId` / `getMatchConfidence` / JPQL `trustTransactionId` / native `trust_transaction_id`; frontend and portal `git grep` of `trustTransactionId` / `matchConfidence`):
- **Response DTO.** `BankStatementLineResponse.of` (`TrustReconciliationService.java:~178-196`) copies both fields onto every line. It is used by the statement GET and by `StatementLinePostingService`. This is the one place a stale suggestion reaches a client.
- **`manualMatch`.** It does not read the suggestion: it takes `lineId` + `transactionId` from the request, requires the line to be UNMATCHED, and overwrites both fields.
- **`releaseMatch` / `unmatch`.** They read `trust_transaction_id` only for AUTO_MATCHED / MANUALLY_MATCHED lines (the guard just before `releaseMatch`). The recorded-line unmatch reads it only for RECORDED lines (`StatementLinePostingService:338-347`). Neither reads an UNMATCHED line's suggestion.
- **Wizard pane.** The FE type carries both fields (`frontend/lib/types/trust.ts:407-408`), but nothing renders or uses them for an UNMATCHED line.
  - `ReconciliationSplitPane.tsx:247-257` builds an UNMATCHED line's candidates from every unmatched transaction of the same absolute amount, not from the suggestion.
  - `page.tsx:370`/`:451` only set the field optimistically after a manual match or unmatch.
  - Correction to the finding's wording: the stale suggestion is not what the UI offers. The pane offers every same-amount unmatched row, contras included (F-652B-1, the pane offers a transfer's contra; still open), whatever is stored. A person can manually match a contra to an unrelated line through the pane with or without a stale suggestion, and that is unchanged by this fix (manual match is out of FU-16's scope).
- **Integrity, report, outstanding and MCP readers.** None. No repository query reads a line's `trust_transaction_id` or `match_confidence`:
  - outstanding items and the books read `trust_transactions.bank_statement_line_id`;
  - G4 counts `match_status = 'UNMATCHED'`;
  - no MCP tool exposes either field.
- **`suggestedClassification` (647C / ADR-380).** It is a separate column, the parser's classification hint for recording a line. It is set at import and cleared only when the line auto-matches (`applyAutoMatch`).
  - It names a classification, not a transaction. It is never written from a candidate pool and does not depend on which rows are candidates.
  - So it is not part of the stale-suggestion problem, and it is untouched.

**Fix.** In `autoMatchStatement`, each locked UNMATCHED line is reset first (`clearSuggestion`: `trust_transaction_id` and `match_confidence` set to null, saved only if something was set), before any tier runs and before the empty-candidates `continue`.
- The tier that applies now writes its result (tier 2 → link at 0.80, tier 3 → row + 0.60, tier 4 → 0.40), or the line stays clean.
- `clearSuggestion` acts only on UNMATCHED lines. The loop holds only UNMATCHED lines, locked in step 1, and the method re-checks the status. MATCHED / RECORDED / EXCLUDED lines are never touched.
- No new lock: the lines were locked in step 1. CF-3 order is unchanged. A refusal at step 3 (RETIRED statement) rolls the resets back with everything else.

**Tests** (seeded through `BankStatementLineRepository`, as a row left by an earlier run looks):
- `autoMatch_clearsAStaleSuggestionOfAContraOnAnUnmatchedLine`: a pre-FU-16 tier-3 suggestion pointing at contra C is cleared.
- `autoMatch_clearsStaleSuggestionsOfALinkedRowAndAnOldAmountOnlyConfidence`: a suggestion of a row since matched by hand to another line, and an old 0.40 with no row, are both cleared.
- Both were RED on 3298250 (`red-stale-suggestion.txt`, full output in `red-stale-suggestion-raw.txt`) and are green now.
- `autoMatch_rewritesAStillValidSuggestionIdentically` (guard, green before and after): a valid tier-3 suggestion (live deposit, 2 days off, alone at its amount) is written identically by a second run — same row, 0.60, status, `matched_count`.

**Exit month.** Unaffected. Every line on G starts UNMATCHED with no suggestion at the single auto-match run, and all 12 matches are tier 1. This is reasoned; the 3298250 E2E is not re-run for this change.
