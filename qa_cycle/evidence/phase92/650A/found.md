| F-1 | `TrustMonthlyListService.lock` / `posted_at` semantics (ADR-382) | **FIXED in the review round (CodeRabbit C1).** Was: a posting stamped `posted_at` before `locked_at` but committed after the lock read the books was in neither the frozen list nor `adjustmentsSinceLock`. Fix: `TrustPostingService.postedNow` takes `SELECT … FOR SHARE` on the trust account row immediately before every `posted_at` stamp (the single choke point, ArchUnit-enforced), and `lock()` takes `FOR UPDATE` on the same row before it reads — so a posting either commits before the list reads or stamps `posted_at` after `locked_at`. Lock order statement → account: `StatementLinePostingService.unmatch` now locks the statement before it reverses rows (it used to post first, which would deadlock with a completion of the same statement); interest/item locks still precede the statement. Side effects: the account-row lock now also serialises postings with `updateTrustAccount` / `closeTrustAccount` (which already claimed to); a long posting transaction (interest run) delays a month-end completion until it commits. Pinned by `TrustMonthlyListIntegrationTest.lockRace_*` (both orders, `pg_blocking_pids`; both fail with the locks removed). | — | done |
