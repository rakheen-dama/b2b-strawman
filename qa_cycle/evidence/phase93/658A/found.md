- **F-658A-1** (MEDIUM?, accounting sync, pre-existing, observed in a test, root cause a hypothesis) In `BroughtForwardFeeNoteIntegrationTest` (tenant with a CONNECTED Xero connection created the `AccountingSyncServiceTest` way), an ordinary fee note created and approved through `POST /api/invoices` → `/lines` → `/approve` (200) had **no** `accounting_sync_entry` row afterwards. The direct call `AccountingSyncService.enqueueInvoicePush(id, EVENT)` in tenant scope does create a PENDING entry for the same fee note. So the event route (`InvoiceApprovedEvent` → `AccountingSyncEventListener.onInvoiceApproved`, `@TransactionalEventListener(AFTER_COMMIT)`, `backend/src/main/java/io/b2mash/b2b/b2bstrawman/integration/accounting/sync/AccountingSyncEventListener.java:30-47`) persisted nothing in this test. **Hypothesis (not proven):** `enqueueInvoicePush` is `@Transactional` (REQUIRED), and it runs inside the AFTER_COMMIT callback. There it joins the already-committed transaction, so its `save` is never committed. That is the documented Spring gotcha, and the reason the notification handlers use `Propagation.REQUIRES_NEW` (e.g. `NotificationService.handleInvoiceVoided`). If so, approve, send and void never enqueue a Xero push in production either. No existing test covers the event route (`AccountingSyncServiceTest` calls the service directly). It needs a focused repro: an approve with a CONNECTED connection, then the `accounting_sync_entry` count. 658A is unaffected, because its guard is the first statement of `enqueueInvoicePush` and is tested by calling the service directly for every `SyncTrigger` (D-248). Fix candidate: `@Transactional(propagation = REQUIRES_NEW)` on the listener path (or on `enqueueInvoicePush` when called from a listener), plus an integration test through `/approve`.
