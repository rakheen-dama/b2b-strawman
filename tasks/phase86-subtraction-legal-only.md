# Phase 86 — Subtraction: Legal-Only Kazi, Archive the Horizontal Platform, Squash Migrations

Phase 86 is a **subtraction phase**. Kazi shipped 83 phases as a horizontal practice-management platform; the product being sold is one vertical profile (South African law firms) and nothing else has a customer. This phase deletes — not gates, not deprecates — every package, route, pack, profile, seeder, scenario, test, compose service and CI job that exists only for accounting firms, agencies, the generic platform story or a superseded implementation: `crm`, `proposal`, `retainer`, `capacity`, `schedule` (recurring half; time reminders re-homed to `timeentry/`), `assistant` (chat + specialists; `provider` re-homed to `integration/ai/provider`), the PayFast *platform* subscription path, the Thymeleaf dev harness, the `docs/` Nextra site, the three non-legal vertical profiles with their packs/seeders/demo seeders, the `deadline/` package, the automation rule *builder*, the stale `frontend/app/portal/**` copy, and the portal `proposals`/`retainer` pages. Each backend removal cuts the exact consumer seams enumerated in architecture §11.3.1–11.3.9, ships its own **throwaway forward drop migration** so the live schema matches the code at every gate (§11.3 intro, §11.3.10(j)), fixes the count-pinning tests in §11.8.3, and lands a named **replacement-path test** proving the surviving legal flow (engagement letter via `DocumentTemplate` + Phase 28 acceptance; billing runs without retainers; notifications without schedules; dashboard without CRM/capacity widgets; AI skills/gates/MCP/Settings → AI without `assistant`; subscription guard without PayFast). Nothing new is built except those drop migrations, the replacement-path tests, a `BaselineSchemaParityTest`, and `backend/db/BASELINE.md`.

The phase exploits a one-time window: **zero production tenants**. Every removal is a true deletion (drop the entity, drop the table), and once slices 2–10 have landed their drops, the entire Flyway series — 133 tenant + 25 global files plus the throwaway drops — is squashed into one `V1__baseline.sql` per series ([ADR-331](../adr/ADR-331-migration-squash-at-zero-tenants.md)), generated by dump-and-hand-clean from a freshly provisioned post-removal tenant and proven byte-equal to a pre-squash `information_schema` snapshot. Sequencing is fixed: **86 → 87 (legal-native shell + API vocabulary) → 84 (take-on lands as V2)**.

This phase ships as **12 epics (595–606)**, one per architecture capability slice (§11.10), expanded to **41 numbered slices** by LAYER: backend removal (package + own tests + compile-critical seams + drop migration), backend residue (string/catalogue seams + count pins + replacement-path test) where the seam count exceeds ~12 surviving files, frontend removal, portal removal where §11.6.6 has entries. **No slice mixes backend + frontend scope.** e2e/QA/compose-seed removals ride with the layer that owns them.

**Migration high-water at phase start**: tenant **V135** (`V135__add_cash_digest_reference_type.sql`), global **V25** (`V25__create_shard_config.sql`) — confirmed by `ls` on 2026-10-15. Phase 86 ships throwaway tenant drop migrations nominally **V136–V142** (§11.7; this breakdown's layer split adds two small ones — `portal_retainer_member_display` and `rate_pack_status` land in separate slices from their package drops — so the expected sequence is V136–V144) and global **V26–V29** (595B added global V29 for 598B's `retainer_updates_enabled` column drop), then squashes everything to **tenant V1 / global V1**; Phase 84 is **V2**. Numbers are nominal: every slice takes the next free number at merge and re-checks on rebase (§11.8.4).
