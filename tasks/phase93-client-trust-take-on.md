# Phase 93 — Client & Trust Take-On: Move a Firm Onto Kazi With Books That Reconcile From Day One

**Status: IN PROGRESS — 9/10 slices Done (653A, PR #1846; 657A, PR #1847 — 2026-11-23; 655A, PR #1850; 655B, PR #1851; 656A, PR #1852; 657B, PR #1853; 657C, PR #1854; 657D, PR #1855; 658A, PR #1857 — 2026-11-24). Next: 660A (capstone).** Breakdown written 2026-11-22 against `origin/main` @ `f73eea861`. A firm (or the founder, white-gloving a pilot) uploads its previous system's exports (CSV or XLSX) under **Settings → Matters → Take-on**, maps the columns, reviews a full dry run, signs where the law puts responsibility, commits, and gets a per-row result report. Four datasets go in dependency order: **clients** (ACTIVE, with a FICA attestation), **matters**, the **trust opening position** (every creditor group plus the bank items outstanding at cutover, gated by the reconciled cutover position and signed off by a partner or director), and **debtor opening balances** (brought-forward fee notes, issued with none of the side effects of sending). The exit bar is the requirements' acceptance invariant: **the first post-cutover reconciliation balances with no manual adjustment**, observed in the browser on a fresh stack (§17.3.13, slice 660A).

### Architecture Decisions
- **A generic mapping wizard over batch / source / row entities, re-runnable, idempotent by dedup keys — no "already ran" flag** (ADR-385, RD-6). One source per trust section, so the trust position is several files committed atomically (§17.2.2).
- **One row model for CSV and XLSX; XLSX streamed, cached values only** (FD-17, §17.6.3).
- **Every take-on read needs the dataset's own capability on top of `MANAGE_TAKE_ON`** — the R-2 trap avoided (§17.10 X1).
- **Summary cards and the row table are read in one `REPEATABLE_READ` transaction** (§17.10 X2).

### Architecture Decisions
- **Opening entries are registry types posted only through `recordOpening`; the registry's `Clearance` is written onto the row as `cleared_at_cutover`, so no SQL needs to know a type** — one predicate in `outstanding` removes the double count (ADR-386, ADR-378 principle).
- **Each item outstanding at cutover is a real, matchable row on the client's matter, paired with a cleared offset** — the creditor's balance is unchanged and a cancelled cheque is an ordinary reversal (§17.3.8).
- **Rows are posted `APPROVED` with the trust signer as approver** — the sign-off is the Rule 54.19 authorisation, and the investment flows require an approved placement (FD-25, ADR-387).
- **The commit is one transaction under the Phase 92 lock order with an in-transaction self-check against the same queries the first reconciliation uses** (§17.3.9).
- **Hard blocks are the five statutory ones and are never overridable; a Fund ledger in debit is a flag** (A4, FD-16, FD-12).
- **The take-on report is an `@Immutable` snapshot of `liveList(G, C)` built in the commit transaction, with rendered files that are never overwritten** (ADR-391, FD-15).
- **The take-on is one brought-forward figure on every movement report, never receipts and payments** (§17.3.15).

### Non-scope
- A write-back wizard for stale cheques (ordinary reversal); synthetic statement lines; a take-on clearing creditor; the opening-balance snapshot escape hatch (Phase 92); the Receipts & Payments running-balance seed for ranges after C (P-21).
