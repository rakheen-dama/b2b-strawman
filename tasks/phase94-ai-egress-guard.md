# Phase 94 — AI Egress Guard: Client Personal Information Leaves Kazi Only Masked, Tokenised, Lawful and On the Record

**Status: PLANNED — 0/9 slices.** Breakdown written 2026-11-28 against `main` @ `382f9f694`. Kazi sends client personal information (PI) to Anthropic by two routes: **route A**, the seven in-product skills (drafting, matter intake, contract review, FICA verification, compliance audit, collection reminder, cash digest) through `AiSkillExecutionService.executeSkill`, and **route B**, the MCP server the firm's own Claude reads. Neither minimises or records anything today. This phase puts **one egress guard** in front of both routes. It always works in the same order: it **blocks** (no transfer basis, a "no AI" client or matter, special personal information, children's personal information, images), it **minimises** (identifiers masked; on route A, names and identifiers are replaced by `[[K:TYPE:n]]` placeholders and swapped back before a human sees the result), and it **records** (one ledger event per skill run or MCP call, holding ids, categories and counts, never a raw value). The record feeds the firm's DSAR answer, its processing register, its PAIA manual and an optional engagement-letter clause. The exit bar is the requirements' two observed items (E8, slice 677A): a live Claude drafting run whose **captured outbound body** holds no raw identifier and no real client name while the approved draft shows the real values, and an MCP session where a sensitive and a "no AI" matter are withheld and correspondence identifiers are masked, after which the client's DSAR export lists every egress event about them.

Backend conventions (§19.2 preamble, `backend/CLAUDE.md`):
- **Entities:** plain `@Entity`, no Lombok, bare `UUID` references, no FK on member / subject / ledger project ids.
- **Append-only records** use static factories with no setters (the `$M/consent/McpEgressConsent.java` shape), and their constructors mirror every DDL CHECK (§19.8.3).
- **Enum columns** are `@Enumerated(EnumType.STRING)` plus a DDL CHECK; jsonb via `@JdbcTypeCode(SqlTypes.JSON)`.
- **Controllers** are one-liners with `@RequiresCapability`. Inject `Clock`. Every refusal is a semantic exception (`InvalidStateException`, `ResourceConflictException`, `ForbiddenException`) → ProblemDetail with the §19.4 codes.
- **Audit:** `egress.*` details go only through `SafeAuditDetails` (ids, enums, ints, booleans, SAFE_TOKEN). Tenancy is schema-per-tenant only: no tenant column, no RLS, no Hibernate filter.

Test conventions:
- Use the standard annotation set `@SpringBootTest @AutoConfigureMockMvc @Import(TestcontainersConfiguration.class) @ActiveProfiles("test") @TestInstance(PER_CLASS)`, embedded Postgres, and an own tenant with a unique `ORG_ID`.
- **No new Spring context key** (FU-8 capped the cache at 12). The one exception is the shared unblock-flag-on property set (P-13).
- Use `TestCustomerFactory` / `TestEntityHelper` / `TestJwtFactory` / `TestMemberHelper` and NEW `$T/testutil/TestEgressHelper` (671A).
- Never assert an exact count over shared-tenant state; scope assertions by id (memory `automation_count_bleed_side_effect_flavor`).
- **Real write path:** every egress integration test drives the same endpoints the UI uses (MockMvc) or the real `executeSkill` / MCP tool beans. No test inserts egress, policy, basis or ledger rows by SQL. The only exception is the direct-JDBC CHECK tests that prove the database rejects a bad row.
